# CLAUDE.md

Project context for Claude Code when working in this Roblox game.

## Project: Burn Rush

A round-based Roblox free-for-all shooter. Every player is armed with a hitscan pistol and a breakable shield; one shot eliminates, a shield blocks one shot, last player standing wins (or everyone still alive wins if the timer runs out). Built with Rojo + Luau.

- **Rojo project**: `default.project.json` (services map to `src/<Service>/`)
- **Toolchain**: `aftman.toml`
- **Scripts**: Luau (`.luau` ModuleScript, `.server.luau` Script, `.client.luau` LocalScript)
- **Style**: Functional modules (no OOP). Each system is a table with `init()` and public functions.

The earlier tag/flamethrower build (burner conversion, stages, fire hazards) lives under `archive/` at the repo root, outside the Rojo tree, for reference only.

## Architecture

### Server (`src/ServerScriptService/`)

- `Main.server.luau`: bootstrap. Requires and `init()`s every system in this order:
  `PlayerState → MapManager → Store → AbilitySystem → CombatSystem → BotSystem → LeanSystem → RagdollSystem → RoundManager`
- `Systems/PlayerState.luau`: per-player state (`Lobby` / `Safe`; eliminated players go back to `Lobby`). Replicates via `PlayerStateChanged` RemoteEvent. Exposes `StateChanged` BindableEvent. `set` also keeps the `IN_ROUND_TAG` (`InRound`) CollectionService tag on the `Player` while it is `Safe`; `BotSystem.spawn` puts the same tag on every bot `Model`, so the tag set is exactly the live combatants (`RagdollSystem` strips it from the corpse clone). Tags replicate on their own, late joiners included; `SpectateController` is the consumer.
- `Systems/RoundManager.luau`: game loop and round lifecycle. Owns the phase state machine, character setup (`BreakJointsOnDeath = false` on every spawn), attaching/detaching the third-person weapon model, elimination handling, and the kill-feed broadcast. Starts/stops `CombatSystem` and `AbilitySystem` together at the Reveal → Round boundary and at round end.
- `Systems/CombatSystem.luau`: the pistol and shield engine. Every combatant is a character `Model`: players resolve to their `Character` at the remote boundary, bots are registered with `registerBot(char)`. Per-combatant shield state (up/cooldown/breaks-in-chain), hitscan shoot handling (the client's hit claim is validated and stands, otherwise a server raycast decides; see Pistol), shield raise/lower/break logic, and the passive Heartbeat step that expires shields and clears cooldowns. `prepareHitbox(char)` (called for every player character and bot at spawn) sets `CanQuery = false` on every accessory part, now and as they load, so only body parts and the shield bubble register on either side. Client-only feedback remotes are skipped for combatants without a Player. `shoot(char, origin, direction)` and `raiseShield(char)` are public for server-driven combatants and apply the same rules as the remotes. Auto-creates `ShootRequest`, `ShieldRequest`, `ShieldChanged`, `ShotBlocked`, `DamageDealt`, `DamageTaken`, `ShotTracer` on `init()` via the `ensureRemote` pattern. Exposes `PlayerEliminated` BindableEvent `(victimChar, killerChar?)`.
- `Systems/BotSystem.luau`: server-driven bots that count as players. `plannedCount()` is `BOT_COUNT` while `BOTS_ENABLED`, else 0; `aliveNames()` lists the bots still standing this round. `spawn()` (called at Reveal) clones `ReplicatedStorage.Assets.Rigs.NPC` `plannedCount()` times onto random spawn points into `Workspace.Bots`, named `Bot1..N`, and registers each with `CombatSystem`. `start()` (at Round) runs two loops per bot: a walk loop that picks a random spawn point and follows a `PathfindingService` path (a waypoint that isn't reached within `BOT_WAYPOINT_TIMEOUT` picks a new destination), and a combat loop that fires at the nearest visible combatant with `BOT_AIM_JITTER` (a random direction if nobody is visible) every `BOT_SHOOT_INTERVAL` and raises its shield every `BOT_SHIELD_INTERVAL`. `remove(char)` destroys an eliminated bot; `stop()` (round end) halts the loops but leaves the models standing so a victim's kill cam can keep tracking its killer through the arena freeze, and `despawn()` (with the lobby teleport) destroys them all. Bots have no walk animation and no weapon model.
- `Systems/LeanSystem.luau`: directional body lean. Every Heartbeat, for every player character and every model under `Workspace.Bots` with an R6 `HumanoidRootPart.RootJoint`, it eases the joint's `C0` toward the rest pose tipped up to `LEAN_MAX_ANGLE` degrees toward the humanoid's `MoveDirection` in root space (pitch forward/back, roll sideways) at `LEAN_RATE`, and back to upright when still. The rest pose is stored on the joint as the `LeanBaseC0` attribute (a Lua table keyed by the Instance loses entries to GC and the lean would accumulate). Server side so the tilt replicates to everyone; the owner sees their own lean one network hop late. Pure target math is `LeanSystem._target(baseC0, localMove)`, checked by `Systems/LeanTest.luau` from the command bar; run it in a play session's Server VM if `Constants` was required earlier in the edit session, since that cache is stale.
- `Systems/RagdollSystem.luau`: the corpse left where a combatant was eliminated. `spawn(victimChar, killerChar?)` (called by `RoundManager.onPlayerEliminated` before the lobby teleport, so only during `Round`; a lobby reset never reaches it) clones the victim (toggling `Archivable`), strips scripts, `ForceField`, `PlayerShield` and the `Animator`, keeps the `Humanoid` but dead with no name tag (shirts, pants and body colors only render through a Humanoid) and switches it to the `Physics` state once the corpse is parented (any standing state keeps holding the torso up; `ChangeState` is a no-op before parenting), converts every Motor6D between direct body parts to a `BallSocketConstraint` limited to `RAGDOLL_JOINT_LIMIT` (the weapon motor stays rigid), copies each body part's CFrame so the death pose is kept, turns `CanQuery` and `CanTouch` off on every part (shots and the test wall ignore corpses) and `CanCollide` on for body parts except the root, sets `RAGDOLL_DENSITY`, hands every part to the server with `SetNetworkOwner(nil)` (auto ownership would give it to the victim's client, which is then teleported out of simulation range and leaves the corpse frozen upright for everyone), gives it the victim's velocity plus `RAGDOLL_IMPULSE` away from the killer (forward when there is none: a perfectly still upright ragdoll sleeps on its feet), and parents it under `Workspace.Ragdolls`, where it stays until `clear()` empties the folder at round end. Bots go through the same path, and so does a player who resets mid-round (see Elimination). `_build(model)` is the pure conversion, checked by `Systems/RagdollTest.luau` against the NPC rig (run it in a play session's Server VM, see LeanSystem).
- `Systems/MapManager.luau`: clones map from `ServerStorage.Maps` into `Workspace.LoadedMap`, manages spawn points and lobby teleport. Warns at `init()` if `ServerStorage.Maps` is missing or empty.
- `Systems/Store.luau`: coins, owned items and equipped choices, persisted in the `STORE_DATASTORE_NAME` DataStore keyed by `UserId`. The record is `{ version, coins, owned = { Weapons = {...}, Abilities = {...} }, equipped = { Weapons = name, Abilities = name } }`. On join it creates `leaderstats.Coins`, loads the record (`STORE_LOAD_RETRIES` attempts, `STORE_RETRY_DELAY` apart; a Studio session without API access gives up at once and runs session-only with one warning) and merges it with the catalog through `Store._merge`: every free item (`price == 0`) is owned, names the catalog no longer has are dropped, and an equipped name that isn't owned falls back to `VIEWMODEL_DEFAULT_WEAPON` or the first owned item. A failed load builds defaults and flags the wallet unsaveable so a bad read never overwrites a good save; coins earned before the load finishes are held and added afterwards. Saves go through `UpdateAsync` on `PlayerRemoving`, `BindToClose`, every `STORE_AUTOSAVE_INTERVAL` seconds (dirty wallets only) and right after a coin pack receipt. `addCoins(player, n)` is called by `RoundManager` per kill (`SHOP_COINS_PER_KILL`) and per win (`SHOP_COINS_PER_WIN`). `ShopPurchase(kind, name)` with `kind` `Weapons` or `Abilities` (`Catalog` kinds) deducts the item module's `price`, marks it owned and equips it. `ShopEquip(kind, name)` switches between owned items of either kind. Every change pushes `ShopState` to the owner. `equipped(player, kind)` is what `RoundManager` welds at spawn and what `AbilitySystem` checks before dashing. Coin packs are developer products: `MarketplaceService.ProcessReceipt` finds the `Items.Robux` module with that `productId`, grants its `coins`, saves, and returns `PurchaseGranted` only once the save succeeded (`NotProcessedYet` if the wallet isn't loaded or saveable, the product is unknown, or the save failed, rolling the coins back). The pure helpers `_merge`, `_purchase` and `_equip` are covered by `Systems/StoreTest.luau`, run from the command bar with `require(game.ServerScriptService.Systems.StoreTest)()`.
- `Systems/AbilitySystem.luau`: dash mechanic for safe players (Q key). Only acts when the player's equipped ability (`Store.equipped(player, "Abilities")`) is `Dash`; any other equipped ability is inert. Cooldown, duration and velocity come from `Abilities.params("Dash")`. The dash goes along `Humanoid.MoveDirection` (WASD, camera-relative, replicated), or forward when standing still. Phase-gated via `start()` / `stop()`: dash is rejected outside the active `Round` phase, so safe players cannot dash during reveal or lobby. `start()` also clears `lastDash` so cooldowns don't carry across rounds.

### Client (`src/StarterPlayerScripts/`)

- `Main.client.luau`: bootstrap. Inits `AbilityHUDController`, `DashController`, `UIController`, `KillFeedController`, `KillConfirmController`, `CombatController`, `CombatFeedbackController`, `ChangeIndicatorController`, `ShopController`, `KillCamController`, `MovementController`, `ShiftLockController`, `MinimapController`, `SpectateController`, `MobileControlsController` (in that order).
- Remotes that identify another combatant (`DamageDealt` victim, `DamageTaken` attacker, `ShotBlocked` other) carry a `Player` for players and the bot `Model` for bots. `KillFeed` carries names only; a bot's name is its model name (`Bot1`).
- The camera is always the **stock Roblox classic camera with a free cursor**; there is no custom camera code outside the kill cam. `StarterPlayer.DevCameraOcclusionMode` is `Zoom` (set in `default.project.json`): the stock popper pulls the camera in front of any wall between it and the character, so the camera never sits behind geometry (Invisicam let it, and the aim ray then hit the wall behind the player). The client aim ray also starts at the character's depth along the camera ray rather than at the camera, so nothing between the camera and the player can become the aim point. `CameraMinZoomDistance` and `CameraMaxZoomDistance` are both 12.5 (also in `default.project.json`), so the scroll wheel cannot change the camera distance. During combat, `ShiftLockController` forces shift lock the way the stock PlayerModule does internally (`UserGameSettings.RotationType = CameraRelative`, `MouseBehavior = LockCenter` re-asserted right after the camera render step, `Humanoid.CameraOffset = SHIFTLOCK_CAMERA_OFFSET`), and releases all three when combat mode ends. The stock `CameraModule` no longer exposes its mouse lock controller (`PlayerModule:GetCameras()` returns `{}`), so it cannot be toggled through the PlayerModule. Shift's built-in mouse-lock toggle is unbound so it never fights the forced lock. While locked, the crosshair sits at the viewport center and aiming is a raycast from the camera through the center; otherwise the crosshair follows the mouse cursor and the ray goes through the cursor.
- `Controllers/MovementController.luau`: client-side movement extras, all gated on combat mode (`CombatController.isCombatActive()`), and the only writer of the camera FOV. **Sprint**: hold Shift while the shield is down: `WalkSpeed` to `SPRINT_WALKSPEED` and FOV eased `CAMERA_FOV` to `SPRINT_FOV` over `SPRINT_FOV_TWEEN_TIME`; the local character is client-simulated, and WalkSpeed is re-applied every frame because the server rewrites it on shield changes. **Aim**: hold right click for FOV `AIM_FOV` over `AIM_FOV_TWEEN_TIME` (FOV only, no speed change); aim wins over sprint for the FOV. **Double jump**: a second jump request while in `Freefall`, at least `DOUBLE_JUMP_DELAY` after leaving the ground, calls `Humanoid:ChangeState(Jumping)` once per airtime; resets on `Landed`. `SHIFTLOCK_CAMERA_OFFSET` is wider than the stock 1.75 so the character sits clear of the centered crosshair. **Movement animations** (not gated on combat): on character bind it preloads every clip with `ContentProvider:PreloadAsync` (in a spawned task, so the jump-state wiring doesn't wait), then loads the six `MOVEMENT_ANIMATIONS` (idle, forward, backward, left and right walks, run) on the humanoid's `Animator` at Movement priority, looping at near-zero weight. The preload matters: a track takes the asset's authored priority and loop flag when its data arrives, which on a live client is after `LoadAnimation` returns, so without it the authored values (several clips are exported as Action or Idle) silently replace what the script set. Studio has the assets cached and never shows this. Every frame the four walk weights come from `MoveDirection` in root space, normalized to sum to the input magnitude; while sprinting the forward share goes to the run track instead; idle takes the rest, and all six drop to near zero while airborne so the stock fall shows. Walk playback speed is horizontal velocity over `MOVEMENT_ANIM_REFERENCE_SPEED`, the run's over `MOVEMENT_RUN_REFERENCE_SPEED`, weights ease over `MOVEMENT_ANIM_FADE`. Movement priority sits above the stock Animate script's Core walk, so no Animate changes are needed. Every frame a movement track that is not playing is played again at epsilon weight: applying the character's appearance shortly after a respawn stops every track on the Animator, and unlike the stock Animate script nothing else would restart ours. One-shots at Action priority: `JUMP_ANIMATION` on every `Jumping` state change (double jump included), and `playDashAnimation()` (called by `DashController` on a dash) plays the `DASH_ANIMATIONS` left or right track when the sideways component of the move direction dominates; a forward or backward dash has no animation.
- `Controllers/MobileControlsController.luau`: touch stand-ins for the combat inputs. Binds the Studio-authored `Game.MobileControls` buttons (found by name anywhere under the frame) `Shoot`, `Shield` and `Dash` to `CombatController.tryShoot`, `CombatController.tryToggleShield` and `DashController.tryDash` (the public functions the mouse and keys call, with every gate inside them), and `Sprint` / `Aim` as toggles over `MovementController.setSprintHeld` / `setAimHeld` (held keys on a keyboard; a held touch button would need a third finger). A toggle that is on swaps its fill and label colors, and every toggle is forced off whenever the frame hides so nothing carries into the lobby or the next round. The frame shows only on a touch device without a keyboard while combat is active (local `Safe`, phase Reveal or Round); the dash button additionally hides unless the equipped ability is Dash. Aiming needs nothing extra: shift lock is forced in combat, so a tapped shot goes through the screen center. Studio reports no touch, so to try it in a play session set the frame `Visible` from the client and click the buttons.
- `Controllers/MinimapController.luau`: drives the Studio-authored `Game.Minimap` frame (`MINIMAP_*` tunables for the dots), visible while the phase is `Reveal` or `Round` and the local player is `Safe` (an eliminated player in the lobby sees no map). Every `RenderStepped` it places one dot per combatant (every player's character plus every model under `Workspace.Bots`) relative to the local player: the local player is always the center, the camera's horizontal look direction is up (so the map turns with the player), and `MINIMAP_RANGE` studs reach the edge; dots beyond that are hidden (eliminated players standing in the lobby). Dot colors: the local player is white, a character with a `PlayerShield` bubble is blue, one that fired within the last `MINIMAP_SHOT_FLASH` seconds is yellow (the server bumps a replicated `Shots` attribute on the shooter's character in `CombatSystem.shoot`), otherwise red.
- `Controllers/SpectateController.luau`: lobby-only spectating behind the `SpectateButton` in `Lobby.Buttons` (bound through `ShopController.bindLobbyButton`, so it hovers and presses like the other two). The `InRound`-tagged instances with a humanoid in `Workspace` (Safe players' characters and bot models) form a ring sorted by name. Clicking picks the first, closes any open modal (`ShopController.closeAll`), hides `Lobby.Buttons` and, every `RenderStepped`, keeps the camera `Custom` with that humanoid as `CameraSubject`: the stock camera orbits the target. While active the `Lobby.Spectate` bar is the only lobby UI: the target's name between `Prev` / `Next` buttons that walk the ring, and `Exit` (`BACK TO LOBBY`) under them. When the target loses the tag or leaves `Workspace` (eliminated, ragdolled, round over) it hands over to the next name in the ring; with none left, on `Exit`, or when the local state leaves `Lobby` (the Reveal teleport), it restores the local humanoid, hides the bar and shows the buttons again if the state is still `Lobby`.
- `Controllers/KillCamController.luau`: on `KillFeed` where the local player is the victim and the killer is another player with a character (or a bot under `Workspace.Bots`), sets the camera `Scriptable`, eases it over `KILL_CAM_TWEEN_TIME` to `KILL_CAM_DISTANCE` studs in front of the killer's head (on the side the victim died on, `KILL_CAM_HEIGHT` up) looking at them, tracks the killer per frame for `KILL_CAM_TIME`, then restores `Custom` on the local humanoid. Ends early if the killer's character goes away. Client only: the server still teleports the victim to the lobby immediately, only the camera stays behind. `play(killerCharacter)` is public so it can be driven against a dummy rig in a solo playtest.
- `Controllers/UIController.luau`: reads phase/player-state remotes, renders RichText into `Game.StatusFrame.Status` (main announcements) and the `Game.SecondaryStatus` pill (`Secondary` + `Alive` chips). During `Round`, Status reads "LAST ONE STANDING" and the pill shows `1:30` on the left and `ALIVE 4/4` on the right: Safe players plus the models under `Workspace.Bots`, over players plus `BOT_COUNT` (when `BOTS_ENABLED`). In other phases the pill shows a single full-width line (`PLAYERS 4/2` counting planned bots, `STARTING IN 5`, `POSITION YOURSELF 8`). At `End`, Status renders the winner banner (1 / 2 / `N PLAYERS SURVIVED!` formats, empty winners falls back to "ROUND ENDED").
- `Controllers/KillFeedController.luau`: listens to `KillFeed` remote, clones `Game.ID_Objects.KillData` into `Game.KillFeed` per kill and positions the rows itself (the feed has no layout object). Rows stack down from the feed's top edge, oldest first: a new kill slides in from the right below the others, and whenever a row leaves, the rows under it tween up one slot over `SHIFT_TIME`; `ROW_GAP` (fraction of the feed height) separates them. After `DISPLAY_TIME` a row fades while sliding fully off the right edge of the screen (`SLIDE_OUT_MARGIN` past its own width) and is destroyed; exceeding `MAX_ENTRIES` evicts the oldest the same way. Text is `"<Killer> shot <Victim>"` when there's a killer, `"<Victim> eliminated"` otherwise.
- `Controllers/KillConfirmController.luau`: pop-up notification ("ELIMINATED <Name>") shown to the killer only when `KillFeed` fires with `killerName == localPlayer.Name`. Clones `Game.ID_Objects.KillConfirm` into `Game` per kill. Each banner has its own independent lifecycle (expand → fade-in → 3s hold → fade-out → collapse): banners do **not** cancel each other. Concurrent kills stack: the newest sits at the template's authored position; older ones reflow by `STACK_DIRECTION` (-1 = upward) × `(height + STACK_GAP)` per slot. Soft cap `MAX_STACK = 5` evicts the oldest banner when exceeded; the evicted banner's coroutine bails on its next `clone.Parent` check after destroy. All stacking tunables are at the top of the file.
- `Controllers/DashController.luau`: sends `DashRequest` on Q, phase-gated to `Round`, state-gated to `Safe`, and only while `AbilityHUDController.equippedAbility()` is `Dash`. Resets `lastDash` to 0 the moment the client sees phase transition into `Round`, so stale cooldowns don't carry across rounds.
- `Controllers/CombatController.luau`: shooting and shield input, and the source of truth for the shield and gun meters. On LMB, raycasts `Camera:ViewportPointToRay` at the mouse cursor out to `PISTOL_RANGE` (excluding the local character) to find the aim point and the part under it, then fires `ShootRequest(Head.Position, direction, aimPoint, hitPart?)`: client-side gated on state `Safe`, phase `Round`, shield not up, and the local `PISTOL_COOLDOWN` timer. On E, fires `ShieldRequest(true)` to raise (only when status is Ready) or `ShieldRequest(false)` to lower (only while Up). Listens to `ShieldChanged(status, duration, breaksInChain)` to drive `Game.Actions.Meters.ShieldMeter.BarBG.Fill`: full and draining to empty over `duration` while Up, empty and filling back up over `duration` while on Cooldown, full and static when Ready. `BarBG.EmptyOverlay` is visible only during Cooldown. `Game.Actions.Meters.GunMeter` has the same children: on every shot sent its `Fill` snaps empty and refills over `PISTOL_COOLDOWN` with `EmptyOverlay` visible until full; it resets to full on every phase change. The meters' parent (`Game.Actions`) is shown only while combat is active - local state `Safe` and phase in `{Reveal, Round}` - so it's visible (but inert) during the Reveal countdown too. Exposes `ShotFired: BindableEvent.Event`, fired with the aim point whenever a shot is actually sent, consumed by `CombatFeedbackController` for the crosshair punch and the shooter's own tracer.
- `Controllers/CombatFeedbackController.luau`: purely cosmetic. Listens to `DamageDealt` (shooter side: throttled hit-confirm sound, batches damage into floating numbers above the victim's head via the `ReplicatedStorage.Assets.UI.DamageNumber` BillboardGui template), `DamageTaken` (victim side: vignette pulse, camera shake via `Humanoid.CameraOffset`, HP-threshold grunts at 75/50/25%, looping sizzle while taking damage), `KillFeed` (kill-confirm whoosh for a kill landed / convert-impact effect when eliminated), `ShotBlocked` (a sound for either party when a shield absorbs a shot), and `ShotTracer` (draws another combatant's tracer). Uses `Game.Vignette` and `Game.Crosshair` GuiObjects. Local-only sound IDs are stubbed (`""`): see the `SOUND_IDS` table at the top of the file when assets are ready. The gunshot and the three shield sounds (raise, lower, break) are played **server side** by `CombatSystem` (a `Sound` parented to the relevant head, so everyone hears them spatially); their IDs are `PISTOL_SHOT_SOUND`, `SHIELD_RAISE_SOUND`, `SHIELD_LOWER_SOUND` and `SHIELD_BREAK_SOUND` in Constants.
  - **Combat mode**: listens to both `PlayerStateChanged` and `RoundStateChanged` for the local player. Active iff `state == Safe AND phase ∈ {Reveal, Round}`. When active, hides the system cursor (`UserInputService.MouseIconEnabled = false`), shows `Game.Crosshair` and moves it to the mouse position every `RenderStepped`. When inactive, restores the cursor, hides the crosshair and resets it to idle. Damage shake writes `Humanoid.CameraOffset` each frame while decaying, additive on top of `ShiftLockController.baseCameraOffset()` (the shoulder offset while locked, zero otherwise), and settles back to that base.
  - **Tracer**: client-drawn. A neon segment `PISTOL_TRACER_LENGTH` long flies at `PISTOL_TRACER_SPEED` from the shooter's muzzle to the end point, stepped on `RenderStepped`, then a `PISTOL_IMPACT_PARTICLES` spark burst plays where it lands. The muzzle is an `Attachment` (or part) named `Muzzle` anywhere in `EquippedWeapon`, else the weapon's primary part, else the head (bots have no weapon). The local shooter draws theirs on `CombatController.ShotFired` to their own aim point; everyone else draws on `ShotTracer`.
  - **Crosshair**: four `Arm` Frames built at `init()` inside the Studio `Game.Crosshair` Frame (whose own background and stroke are disabled; it is only the mouse-following anchor). Idle by default, punched (the anchor's size tween spreads the arms, and each arm's color tweens; reverses automatically) on `CombatController.ShotFired`. Arm length, thickness and colors are the `CROSSHAIR_*` tunables at the top of the file.

### Character (`src/StarterCharacterScripts/`)

- `Health.client.luau`: empty override of Roblox's default Health script. Disables passive HP regen so damage persists between encounters.

### Shared (`src/ReplicatedStorage/`)

- `Shared/Constants.luau`: all tunables (round timing, pistol/shield numbers, movement, shop economy and DataStore timing, state and phase strings, UI colors, shield status strings, end reasons). Per-item tunables (price, stats, ability params, weapon grip) live in the item modules under `Items` instead.
- `Shared/Catalog.luau`: the item catalog. Every ModuleScript under `ReplicatedStorage.Items.<Kind>.<Name>` (kinds `Weapons`, `Abilities`, `Robux`; source under `src/ReplicatedStorage/Items/<Kind>/<Name>/init.luau`) is one item returning `{ displayName, price?, description?, stats? = { { label, value }, ... }, params? (abilities), grip? (weapons), gamePassId? / productId? + coins? (Robux) }`. Studio-authored children ride along inside the module (every folder has `ignoreUnknownInstances`): a weapon's `Model`, an ability's or Robux item's `Icon` ImageLabel. `Catalog.items(kind)` (sorted by price then name), `Catalog.get(kind, name)`, `Catalog.model(kind, name)`, `Catalog.icon(kind, name)`, `Catalog.free(kind)`. Read once on first use; a module that errors or doesn't return a table is warned about and skipped.
- `Shared/Types.luau`: Luau type aliases: `PlayerStateName` (`"Lobby" | "Safe"`), `RoundPhase`, `EndReason`, `RoundEndExtra`.
- `Shared/Abilities.luau`: thin wrapper over the catalog's `Abilities` kind. `Abilities.get(id)` resolves an item into an `AbilityDef` (`displayName` from the module, icon image and color from its `Icon` child), `Abilities.params(id)` returns the module's `params` (`DEFAULT_PARAMS` when absent). Only Dash has behavior; other abilities can be bought and equipped but are inert.

### Remotes (`ReplicatedStorage.Remotes`)

The `Remotes` folder lives in Studio (not Rojo source); it is preserved across syncs because `ReplicatedStorage` has `ignoreUnknownInstances: true`. Several remotes are **auto-created** by their owning system if missing (the `ensureRemote` pattern), so you don't have to author them in Studio.

- `RoundStateChanged` (RemoteEvent): server broadcasts `(phase, duration?, extra?)`. During `Reveal` and `Round`, `extra` is `nil`. At `End`, `extra` is `{ winners = { name, ... }, reason }`: `winners` is empty when `reason == "Aborted"`.
- `PlayerStateChanged` (RemoteEvent): server broadcasts `(player, state)`.
- `DashRequest` (RemoteEvent): client → server.
- `ShootRequest` (RemoteEvent): client → server `(origin: Vector3, direction: Vector3, aimPoint: Vector3, hitPart: BasePart?)`. `origin` is the client's Head position, `aimPoint` where the crosshair ray ended and `hitPart` what it hit (nil on a miss). Server rejects if `origin` is more than `PISTOL_ORIGIN_TOLERANCE` studs from the server-side head, if `direction` isn't a finite non-zero vector, if the round isn't active, if the shooter isn't `Safe`, if their shield is up, or if they're still on `PISTOL_COOLDOWN`. Auto-created by `CombatSystem.init()`.
- `ShieldRequest` (RemoteEvent): client → server `(raise: boolean)`. `true` raises (rejected if already up, on cooldown, round inactive, or not `Safe`); `false` lowers manually and starts the cooldown. Auto-created by `CombatSystem.init()`.
- `ShieldChanged` (RemoteEvent): server → owning client only `(status, duration, breaksInChain)`. `status` is one of `Constants.SHIELD_UP` / `SHIELD_COOLDOWN_STATUS` / `SHIELD_READY`; `duration` is how long that status lasts (0 for Ready). Sent on every transition (raise, natural expiry, manual lower, break, cooldown ending) and once each on `CombatSystem.start()` / `stop()` as Ready. Auto-created by `CombatSystem.init()`.
- `ShotBlocked` (RemoteEvent): server → both parties `(otherPlayer: Player)`, sent when a shield absorbs a shot: to the shooter with the victim, to the victim with the shooter. Auto-created by `CombatSystem.init()`.
- `DamageDealt` (RemoteEvent): server → shooter `(victim: Player | Model, dmg, victimHP)` on a landed, unblocked shot. `victimHP` is the HP after the shot (0 on elimination). Auto-created by `CombatSystem.init()`.
- `DamageTaken` (RemoteEvent): server → victim `(attacker: (Player | Model)?, dmg, currentHP)`, same moment as `DamageDealt`. Auto-created by `CombatSystem.init()`.
- `ShotTracer` (RemoteEvent): server → every client except the shooter `(shooter: Model, endPoint: Vector3)` on every accepted shot; the shooter draws their own tracer on input. Auto-created by `CombatSystem.init()`.
- `KillFeed` (RemoteEvent): server broadcasts `(killerName?, victimName)` per elimination. Auto-created by `RoundManager.init()`.
- `ShopState` (RemoteEvent): server → owning client `({ coins, owned = { [kind] = { name, ... } }, equipped = { [kind] = name } })` once the record is loaded and after every coin or item change. `ShopController` renders it; `AbilityHUDController` reads `equipped.Abilities` from it. The client also fires it with no arguments to ask for a fresh copy (the join-time push can beat the controller). Auto-created by `Store.init()`.
- `ShopPurchase` (RemoteEvent): client → server `(kind, name)`; `ShopEquip` (RemoteEvent): client → server `(kind, name)`. `kind` is a `Catalog` kind (`Weapons` / `Abilities`); validated against the catalog, ownership and coin balance. Auto-created by `Store.init()`.
- `FireRequest`, `FuelChanged`, `InfectionProgress`: no longer used by any active system; don't create or reference them (kept only to avoid Studio-side cleanup on old saves).

## Round Flow

`Lobby → Intermission (10s) → Reveal (10s) → Round (90s) → End (3s arena freeze + 5s lobby = 8s) → Lobby`

`gameLoop` loads the map **before** broadcasting `Intermission`. If the map fails to load (no `ServerStorage.Maps`, or it's empty), it warns and stays in the `Lobby` phase instead of getting stuck cycling through intermission.

**Reveal phase** is a no-damage, no-shield, no-dash positioning window (`REVEAL_TIME = 10s`). Every player is set `Safe` and teleported into the arena, but `CombatSystem` and `AbilitySystem` aren't started until Reveal ends, so `ShootRequest`/`ShieldRequest`/`DashRequest` are all rejected server-side, and the client's own phase gates (`currentPhase ~= PHASE_ROUND`) stop it from even sending them.

**Round phase** (`ROUND_TIME = 90s`) is when `CombatSystem.start()` and `AbilitySystem.start()` run. Bots count as players throughout: the round starts once lobby players plus `BotSystem.plannedCount()` reach `MIN_PLAYERS`, and it ends early when Safe players plus alive bots is one or fewer (`REASON_LAST_STANDING`; the survivor, player or bot, is the sole winner) or when server players plus planned bots drop below `MIN_PLAYERS` (`REASON_ABORTED`, winners empty). Otherwise it runs the full 90s and every remaining Safe player and alive bot wins (`REASON_SURVIVED`). A player winner gets `SHOP_COINS_PER_WIN`; a bot winner only gets the banner. `survivorNames()` is players then bots.

**End phase** is a single 8-second window split server-side into two halves:
1. **Arena freeze (`END_DELAY_TIME = 3s`)**: `CombatSystem.stop()` and `AbilitySystem.stop()` run first (this strips every `PlayerShield` bubble), then every character's third-person weapon is detached, then every character gets an invisible `ForceField` named `RoundEndForceField` (belt-and-suspenders invincibility against any in-flight shot), and `RoundStateChanged(PHASE_END, END_DELAY_TIME + END_TIME, { winners, reason })` is broadcast **immediately**. Players are still standing in the arena, but combat mode deactivates client-side (phase ∉ {Reveal, Round}) so the crosshair hides and the meter disappears. The single phase broadcast covers both halves so the End-phase timer reads correctly on the client.
2. **Lobby announcement (`END_TIME = 5s`)**: players are healed to MaxHealth, `RoundEndForceField`s are stripped, everyone is teleported to lobby + set to `STATE_LOBBY`, the bots are despawned, and the map is unloaded. The winner banner remains visible in the lobby for the remaining 5s before the next `gameLoop` iteration broadcasts `PHASE_LOBBY`.

`endRound` is the function that orchestrates this: it stops systems (Combat, Ability, Bot) → detaches weapons → adds ForceFields → broadcasts `PHASE_END` (with the full 8s duration) → `task.wait(END_DELAY_TIME)` → heals + strips ForceFields + teleports + `setLobby` → despawns bots → unloads map → `task.wait(END_TIME)`.

**Test mode** (`Constants.TEST_MODE`, off; the real rules above apply): when on, rounds start with 1 player, the round timer and last-standing checks are skipped, and the round ends when a `Safe` player's character touches any part named `Constants.TEST_END_WALL` (`ShortWall`) in the loaded map, or when no real player is `Safe` any more. The end reason is always `Survived`. Solo play no longer needs it: with `BOTS_ENABLED` and `BOT_COUNT = 3` one real player plus the bots satisfies `MIN_PLAYERS`, and the bots finish a round among themselves if the player dies. Set `BOTS_ENABLED = false` to play without them.

## Pistol

Hitscan, third-person aiming at the mouse cursor, one press per shot (no hold-to-fire).

- **Client**: on LMB, `CombatController` raycasts `Camera:ViewportPointToRay` at the mouse cursor out to `PISTOL_RANGE`, excluding the local character; the aim point is the hit position or the ray's far end. `direction = (aimPoint - Head.Position).Unit`, sent as `ShootRequest(Head.Position, direction, aimPoint, hitPart?)`. Client-side gates: state `Safe`, phase `Round`, shield not up, local `PISTOL_COOLDOWN` timer elapsed.
- **Server** (`CombatSystem.shoot`): re-validates everything the client already checked, plus `PISTOL_ORIGIN_TOLERANCE` (rejects if the claimed origin is too far from the server-side head) and re-normalizes/validates `direction` as a finite, non-zero vector. Then the **hit claim**: if `hitPart` belongs to a live combatant other than the shooter, `aimPoint` is within `PISTOL_RANGE` and within half the part's diagonal plus `PISTOL_HIT_TOLERANCE` studs of the part's server position, and a raycast from `origin` to `aimPoint` (excluding shooter and victim) hits nothing, that combatant is the victim and `aimPoint` the end point. The shooter's screen decides, so lag and camera-vs-head parallax don't eat hits; the tolerance bounds what a forged claim can reach to roughly what lag already allows. Any failed check, or no claim, falls back to raycasting `origin → direction * PISTOL_RANGE`, excluding the shooter's character.
- **Hitboxes**: `prepareHitbox` turns `CanQuery` off on every accessory part of every combatant, so hats, hair and the welded weapon never count. Body parts and the `PlayerShield` bubble are the only things a shot can land on.
- **Damage**: `PISTOL_DAMAGE` (100, one shot eliminates) applied only on a direct hit against another `Safe` player. A hit against a raised shield calls `breakShield` instead of dealing damage (see Shield below).
- **Tracer**: on every accepted shot (hit or miss), the server fires `ShotTracer(shooter, endPoint)` to every client except the shooter; the shooter's own client drew its tracer on input. Each client animates the segment from the muzzle to the end point and sparks on arrival (see `CombatFeedbackController`). Nothing tracer-related is created on the server.
- **Cooldown**: `PISTOL_COOLDOWN` (1.0s) between shots, checked server-side with `PISTOL_COOLDOWN_TOLERANCE` (0.05s) slack for network jitter.

## Shield

Raise it with E; it blocks exactly one shot, then breaks.

- **Raising**: welds a `Part` named `PlayerShield` to the root part (a `SHIELD_SIZE`-stud ball, `Material = ForceField`, `SHIELD_COLOR`, `SHIELD_TRANSPARENCY`, no collision, massless, `CanQuery` on so shots hit the bubble and resolve to its owner). The bubble pops in: it spawns at `SHIELD_RAISE_FX_START` scale and fully opaque, then tweens (Back out) to full size and `SHIELD_TRANSPARENCY` over `SHIELD_RAISE_FX_TIME`. Plays `SHIELD_RAISE_SOUND` at the head, and sets `Humanoid.WalkSpeed` to `SHIELD_WALKSPEED` (12, down from `SAFE_WALKSPEED` 16). Rejected if already up, on cooldown, the round isn't active, or the player isn't `Safe`. While the shield is up the player cannot shoot: the server rejects `ShootRequest` and the client doesn't even send it.
- **Duration: shrinking re-raise**: a freshly raised shield lasts `SHIELD_DURATIONS[1]` (1.0s). Each time it's *broken* by an incoming shot (not lowered manually, not expired naturally), `breaksInChain` increments and the next raise uses `SHIELD_DURATIONS[1 + breaksInChain]` (clamped to the array, 0.5s after one break, 0.25s after two or more). The chain resets to 0 breaks once `os.clock() - lastBreakAt > SHIELD_CHAIN_RESET` (5.0s), so pressure only stays cheap if the defender keeps re-raising fast; a gap resets them to the full 1s shield.
- **Natural expiry or manual lower**: either one removes the bubble (leaving an anchored `ShieldLowerFx` copy that shrinks to `SHIELD_LOWER_FX_SCALE` and fades over `SHIELD_LOWER_FX_TIME`), plays `SHIELD_LOWER_SOUND`, restores `SAFE_WALKSPEED`, and starts `SHIELD_COOLDOWN` (3.0s) before the player can raise again: `ShieldChanged` fires `SHIELD_COOLDOWN_STATUS` immediately, then `SHIELD_READY` once the cooldown elapses.
- **Break** (a landed shot hits a raised shield): the bubble is removed immediately and replaced by a short anchored `ShieldBreakFx` copy that swells by `SHIELD_BREAK_FX_SCALE` and fades over `SHIELD_BREAK_FX_TIME`, emits `SHIELD_BREAK_PARTICLES` cyan shards from a `ParticleEmitter`, and drops a Neon `ShieldBreakRing` cylinder at the owner's feet that expands to `SHIELD_BREAK_RING_SIZE` and fades over `SHIELD_BREAK_RING_TIME`, `SHIELD_BREAK_SOUND` plays at the head, `breaksInChain += 1`, `lastBreakAt = now`, and, critically, there is **no cooldown**. `ShieldChanged` fires `SHIELD_READY` right away, so the player can re-raise on the very next input, just with the shorter duration from the chain. `ShotBlocked` fires to both the shooter and the (former) shield holder.
- The Heartbeat `step` in `CombatSystem` is what actually expires an up shield past `expiresAt` and clears a cooldown past `cooldownUntil`: both paths funnel through `lowerShield`/status broadcasts so the client meter always matches server state.

## Elimination

Players are **never killed** in the Roblox sense. When a `Safe` player's HP reaches 0 from a landed shot:
- HP is restored to `MaxHealth`.
- `CombatSystem.PlayerEliminated` fires `(victim, killer?)`.
- `RoundManager.onPlayerEliminated`, gated to `currentPhase == PHASE_ROUND`, broadcasts `KillFeed(killerName?, victimName)`, spawns the ragdoll corpse at the death spot (`RagdollSystem.spawn`), then sets the victim to `STATE_LOBBY` and teleports them to the lobby (they spectate from there).
- `Humanoid.BreakJointsOnDeath` is set `false` on every spawn so a 0-HP frame never triggers ragdoll or a death animation.
- A player who dies for real while `Safe` (a reset, or anything else that zeroes the humanoid) is handled by the humanoid's `Died` connection made in `onCharacterAdded`. During `Round` it goes through `onPlayerEliminated(char, nil)`: kill feed reads `"<Victim> eliminated"`, a ragdoll is left, state flips to `Lobby`. During `Reveal` it only flips the state to `Lobby`. Every death, in any phase, is followed by `player:LoadCharacter()` at once, so a dead body never lies stiff waiting for the respawn timer (in the arena the ragdoll clone is the only body left behind), and after an arena death the new character spawns in the lobby because the state is already `Lobby`. Roblox does not respawn a second time after the manual load.

`killerName` is always present for a pistol elimination (cone/hazard kills don't exist in this mode); it's only `nil` in the remote's shape for forward-compatibility with `KillFeedController`'s no-killer text path.

## Visual identity

- **Third-person weapon**: `RoundManager.setSafe` welds a clone of `Catalog.model("Weapons", Store.equipped(player, "Weapons"))` (the `Pistol` by default: `VIEWMODEL_DEFAULT_WEAPON` is the free weapon everyone owns; named `EquippedWeapon`) onto the character's right arm via a `Motor6D`, using the grip `CFrame` and motor name read from the matching rig under `ReplicatedStorage.ThirdPersonRigs`. Without a rig it uses the item module's `grip` (identity if absent) + `"Weapon"`. Every other part in the model is welded to the primary part with its authored offset, so a weapon authored as loose parts (the Pistol) holds together. Convention: the weapon's forward axis runs down the arm's -Y, its top faces the arm's -Z, and the grip sits about 0.72 studs below the arm center. `setLobby` and round end both detach it.
- **Shield**: the cyan `PlayerShield` bubble is the only visual: see Shield above. No outline/highlight system exists in this mode (there's no "who's the burner" to call out; everyone looks the same).

## Map Authoring

Maps live in `ServerStorage.Maps` (each is a `Model`). At runtime they are cloned into `Workspace.LoadedMap` (a Folder created on demand). `MapManager.unloadMap()` destroys the whole folder, so even if the `currentMap` reference is lost no orphan parts can survive.

- `SpawnPoints/` folder containing `BasePart`s named `SpawnPoint`.

## Conventions

- New tunables go in `Constants.luau`, except per-item ones (price, stats, ability params, weapon grip), which go in that item's module under `Items`. Don't hardcode magic numbers in systems.
- New shop item: add `src/ReplicatedStorage/Items/<Kind>/<Name>/init.luau` plus an `init.meta.json` with `ignoreUnknownInstances`, sync, then drop the `Model` (weapons) or `Icon` ImageLabel (abilities, Robux) inside the ModuleScript in Studio. Nothing else needs registering.
- New cross-system signals: prefer `BindableEvent` over polling. Existing examples: `PlayerState.StateChanged`, `CombatSystem.PlayerEliminated`.
- Server creates Workspace instances; they replicate to clients automatically. No remote needed for visual effects (see the pistol tracer).
- Per-frame work goes through `RunService.Heartbeat` (server) or `RenderStepped` (client).
- Phase changes broadcast via the existing `RoundStateRemote` `extra` payload: add fields rather than creating new remotes for round metadata.
- Need a new RemoteEvent? Use the `ensureRemote(parent, name)` pattern at the top of `CombatSystem.luau`: it returns the existing remote if present, else creates one. Don't rely on Studio-authored remotes for new functionality.
- UI text colors: use `colorize(color, text)` helper in `UIController` to wrap text in RichText `<font>` tags. Both labels have `RichText = true` set automatically on first resolve.
- Cosmetic-only client feedback (sounds, screen shake, vignette, damage numbers) belongs in `CombatFeedbackController`: driven by `DamageDealt` / `DamageTaken` / `KillFeed` / `ShotBlocked` remotes. Don't add gameplay logic here; if a feature needs server authority, route it through the existing remotes instead.

## Testing

In Studio, use **Test → Local Server → 2 Players** for end-to-end testing. To shorten iteration, temporarily lower `ROUND_TIME` in `Constants.luau`. A plain **Play** session works solo with the default `BOTS_ENABLED`: you plus the bots meet `MIN_PLAYERS`, the round runs under the real rules, and it ends when one combatant is left (or on the timer). Turn `TEST_MODE` on only when you want the `ShortWall` trigger and no last-standing rule.

Rojo's file watcher in this OneDrive folder reliably reports created and deleted files but drops plain modifications: after editing a file, check the Studio copy actually changed. Deleting and recreating a file makes the plugin add a second instance next to the stale one instead of replacing it, so don't use that as a workaround; set `.Source` from the command bar or reconnect Rojo instead.

Module state is per-VM: `require` from the command bar or the MCP plugin returns a *fresh* copy of a system, not the one `Main.server` is running, so calling `CombatSystem.shoot` or `BotSystem.remove` from there does not touch live state. Drive tests through the remotes and Workspace instead.

1. After intermission, the 10s Reveal countdown begins: Status shows "GET READY!", secondary shows a positioning countdown. LMB does not fire a shot (no tracer, no `DamageDealt`/`DamageTaken`), E does not raise a shield, and Q does not dash. The `Actions` cluster and the minimap are already visible (meters full and idle); the lobby `SHOP` / `INVENTORY` buttons are gone.
