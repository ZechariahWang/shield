# CLAUDE.md

Project context for Claude Code when working in this Roblox game.

## Project: Burn Rush

A Roblox free-for-all deathmatch shooter with respawns. Every player is armed with a hitscan pistol and a breakable shield; one shot eliminates, a shield blocks one shot. A killed player returns to the lobby and spawns back in after a short delay; the first combatant to `KILL_TARGET` kills wins the match, or the top scorer when the timer runs out. Built with Rojo + Luau.

- **Rojo project**: `default.project.json` (services map to `src/<Service>/`)
- **Toolchain**: `aftman.toml`
- **Scripts**: Luau (`.luau` ModuleScript, `.server.luau` Script, `.client.luau` LocalScript)
- **Style**: Functional modules (no OOP). Each system is a table with `init()` and public functions.

The earlier tag/flamethrower build (burner conversion, stages, fire hazards) lives under `archive/` at the repo root, outside the Rojo tree, for reference only.

## Architecture

### Server (`src/ServerScriptService/`)

- `Main.server.luau`: bootstrap. Requires and `init()`s every system in this order:
  `PlayerState → MapManager → MatchScore → Store → AbilitySystem → CombatSystem → GrappleSystem → BotSystem → LeanSystem → RagdollSystem → RoundManager`
- `Systems/PlayerState.luau`: per-player state (`Lobby` / `Safe`; `Lobby` covers waiting between matches, before the first spawn and after every death). Replicates via `PlayerStateChanged` RemoteEvent. Exposes `StateChanged` BindableEvent. `set` also keeps the `IN_ROUND_TAG` (`InRound`) CollectionService tag on the `Player` while it is `Safe`; `BotSystem.spawn` puts the same tag on every bot `Model`, so the tag set is exactly the live combatants (`RagdollSystem` strips it from the corpse clone). Tags replicate on their own, late joiners included; `SpectateController` is the consumer.
- `Systems/RoundManager.luau`: game loop and match lifecycle (see Match Flow). Owns the phase state machine (`Lobby` / `Round` / `End`), character setup (`BreakJointsOnDeath = false` on every spawn; every new character starts in the lobby), attaching/detaching the third-person weapon model (through `WeaponModel` with the player's equipped weapon), the `SpawnRequest` handling (`spawnIntoArena`), elimination handling (kill feed, score, coins, ragdoll, back to the lobby), the per-player last-death times behind `RESPAWN_DELAY`, and the kill-feed broadcast. `runMatch` starts `CombatSystem`, `AbilitySystem`, `GrappleSystem` and the bots when the `Round` phase begins and `endRound` stops them. `enoughPlayers()` needs at least one real player on the server plus players and planned bots reaching `MIN_PLAYERS`.
- `Systems/MatchScore.luau`: kills and deaths per combatant for the running match, keyed by name (a player's name, a bot's generated name). `reset()` (start of every match), `addKill(name)`, `addDeath(name)`, `leader()` (the top scorer's name and kills, nil and 0 with no kills; a tie goes to whoever reached the count first) and `targetReached()` (the leader has `KILL_TARGET` kills). The scores replicate as attributes on the Folder `ReplicatedStorage.MatchScores` (created by `init()`): `Kills_<name>` and `Deaths_<name>` per combatant plus `LeaderName`, `LeaderKills` and `Top` (the `TOP_BOARD_SIZE` leading names, comma-joined, in order), so clients and late joiners need no remote. The ordering and tie-break logic are the pure `_new`, `_addKill`, `_kills`, `_addDeath`, `_deaths`, `_leader`, `_top` and `_targetReached` over a plain table, covered by `Systems/MatchScoreTest.luau` (run in a play session's Server VM, see LeanSystem).
- `Systems/CombatSystem.luau`: the pistol and shield engine. Every combatant is a character `Model`: players resolve to their `Character` at the remote boundary, bots are registered with `registerBot(char)`. Per-combatant shield state (up/cooldown/breaks-in-chain), hitscan shoot handling (the client's hit claim is validated and stands, otherwise a server raycast decides; see Pistol), shield raise/lower/break logic, and the passive Heartbeat step that expires shields and clears cooldowns. `prepareHitbox(char)` (called for every player character and bot at spawn) sets `CanQuery = false` on every accessory part, now and as they load, so only body parts and the shield bubble register on either side. Client-only feedback remotes are skipped for combatants without a Player. `shoot(char, origin, direction)` and `raiseShield(char)` are public for server-driven combatants and apply the same rules as the remotes. Auto-creates `ShootRequest`, `ShieldRequest`, `ShieldChanged`, `ShotBlocked`, `DamageDealt`, `DamageTaken`, `ShotTracer` on `init()` via the `ensureRemote` pattern. Exposes `PlayerEliminated` BindableEvent `(victimChar, killerChar?)`. `revive(char)` clears a character's eliminated mark and shield state and sends the owner `Ready`: a player is never really killed, so the same character comes back on every spawn and `CombatSystem` would otherwise still treat it as eliminated (unable to shoot or be hit); `RoundManager` calls it on every spawn. `protect(char)` puts a visible `ForceField` named `SpawnProtection` on the character for `SPAWN_PROTECTION_TIME` (removed by `Debris`); `shoot` ignores a hit on a protected victim (the tracer still draws and the shield is untouched) and removes the shooter's own protection when they fire. Players (through `RoundManager`) and bots (through `BotSystem`) are protected on every spawn.
- `Systems/BotSystem.luau`: server-driven bots that count as players; lifecycle only, the behavior lives in the modules below. `plannedCount()` is `BOT_COUNT` while `BOTS_ENABLED`, else 0; `isBot(char)`. A bot is an identity (generated name plus skill) that lasts the match; each life is a fresh model. `spawn()` (called when the `Round` phase begins) rolls `plannedCount()` identities (`BotAppearance.randomName`, `BotBrain._rollSkill`) and spawns each one's first life: a clone of `ReplicatedStorage.Assets.Rigs.NPC` on the spawn point farthest from every live combatant (`MapManager.spawnCFrameAwayFrom`) into `Workspace.Bots`, named with the identity (also the humanoid `DisplayName`), with the `InRound` tag, `CombatSystem.registerBot`, spawn protection, the default pistol (`WeaponModel.attach`), the players' movement animations (`BotAnimator.attach`) and a random avatar (`BotAppearance.apply`, rolled again each life). `start()` hands every bot to `BotBrain` (a life spawned while running gets its brain at once); `remove(char)` destroys an eliminated bot and, while the match runs, schedules its next life under the same name `RESPAWN_DELAY` later (a `generation` counter bumped at every `stop()` drops a respawn scheduled in an earlier match), so its score carries on; `stop()` (match end) clears the brains and identities but leaves the models standing so a victim's kill cam can keep tracking its killer through the arena freeze, and `despawn()` (with the lobby teleport) destroys them all.
- `Systems/BotBrain.luau`: one behavior loop per bot, stepped on Heartbeat between `start` and `stop`. Skill (rolled at spawn inside the `BOT_REACTION_TIME`, `BOT_AIM_ERROR`, `BOT_AGGRESSION`, `BOT_SHIELD_SENSE` ranges) sets how fast a bot reacts, how much it misses, how hard it pushes and how often it blocks. **Perception** every `BOT_PERCEPTION_INTERVAL`: the nearest combatant (Safe players plus other bots) with line of sight from the head within `PISTOL_RANGE` becomes the target; the last sighting's position and time are remembered. **Engaged** (target in view): `AutoRotate` off and the root yaw eased toward the target at `BOT_TURN_RATE`; `Humanoid:Move` strafes sideways, flipping every `BOT_STRAFE_SWITCH`, plus closing in above `BOT_ENGAGE_DISTANCE[2]` or backing off below `[1]`; a hop every `BOT_JUMP_INTERVAL` divided by (0.5 + aggression). `MoveDirection` replicates, so `LeanSystem` and `BotAnimator` read it like a player's. **Shooting**: the first shot waits the reaction time from first sight; every shot aims at the torso with `_aimError` radians of error (the rolled base scaled by sqrt(distance / `BOT_AIM_REFERENCE_DISTANCE`), up with target speed via `BOT_AIM_SPEED_PENALTY`, down with time tracked via `BOT_AIM_SETTLE_RATE`), never while its own shield is up, `PISTOL_COOLDOWN` plus `BOT_FIRE_HESITATION` apart; misses come from the error. **Shield**: a threat is the target facing the bot within `BOT_THREAT_ANGLE` with a ready gun; the bot rolls its shield sense when the threat starts and every `BOT_THREAT_REROLL` while it lasts, and a won roll raises after the reaction time; a break (`CombatSystem.lastBreakAt` moved) re-raises at once with probability aggression; a raised shield is dropped to shoot back the moment the target's gun goes on cooldown. **Roaming** (no target): a `PathfindingService` path to the last sighting while it is younger than `BOT_MEMORY_TIME`, else to a random spawn point, `MoveTo` per waypoint with `BOT_WAYPOINT_TIMEOUT` (stuck: new destination), at `SPRINT_WALKSPEED` while more than `BOT_SPRINT_LEG` studs remain. Every shot and shield goes through `CombatSystem`, so the rules are the players'. The pure helpers `_rollSkill`, `_aimError`, `_holdMove` and `_facing` are covered by `Systems/BotBrainTest.luau` (run in a play session's Server VM).
- `Systems/BotAnimator.luau`: server-side movement animations for bots: an `Animator` on each bot's humanoid loads the six `MOVEMENT_ANIMATIONS` (Movement priority, looped) and `JUMP_ANIMATION` (Action, on every `Jumping` state) and steps the weights every Heartbeat with `Shared/MovementBlend`, sprinting when `WalkSpeed` is `SPRINT_WALKSPEED`; tracks loaded on the server replicate. A clip's authored priority and loop flag replace what was set once its data arrives, so the step re-asserts them (the client preloads instead).
- `Systems/BotAppearance.luau`: `randomName(taken)` builds a username from `BOT_NAME_ADJECTIVES` / `BOT_NAME_NOUNS` with a number or `xX..Xx` style, unique against the round and the server's players. `apply(char)` sets random body colors at once and, in a background task, fetches `GetHumanoidDescriptionFromUserId` for up to `BOT_AVATAR_TRIES` random ids in `BOT_AVATAR_USER_ID_RANGE` and applies the first that works (Studio needs API access; the colors stay otherwise), storing that id as the `AvatarUserId` attribute on the model for the top board's headshot. Accessories get `CanQuery` off through `prepareHitbox` as they arrive.
- `Systems/WeaponModel.luau`: `attach(char, weaponName)` / `detach(char)`: the third-person weapon welded to the right arm (see Visual identity). `RoundManager` uses it with the equipped weapon, `BotSystem` with `VIEWMODEL_DEFAULT_WEAPON`.
- `Systems/LeanSystem.luau`: directional body lean. Every Heartbeat, for every player character and every model under `Workspace.Bots` with an R6 `HumanoidRootPart.RootJoint`, it eases the joint's `C0` toward the rest pose tipped up to `LEAN_MAX_ANGLE` degrees toward the humanoid's `MoveDirection` in root space (pitch forward/back, roll sideways) at `LEAN_RATE`, and back to upright when still. The rest pose is stored on the joint as the `LeanBaseC0` attribute (a Lua table keyed by the Instance loses entries to GC and the lean would accumulate). Server side so the tilt replicates to everyone; the owner sees their own lean one network hop late. Pure target math is `LeanSystem._target(baseC0, localMove)`, checked by `Systems/LeanTest.luau` from the command bar; run it in a play session's Server VM if `Constants` was required earlier in the edit session, since that cache is stale.
- `Systems/RagdollSystem.luau`: the corpse left where a combatant was eliminated. `spawn(victimChar, killerChar?)` (called by `RoundManager.onPlayerEliminated` before the lobby teleport, so only during `Round`; a lobby reset never reaches it) clones the victim (toggling `Archivable`), strips scripts, `ForceField`, `PlayerShield` and the `Animator`, keeps the `Humanoid` but dead with no name tag (shirts, pants and body colors only render through a Humanoid) and switches it to the `Physics` state once the corpse is parented (any standing state keeps holding the torso up; `ChangeState` is a no-op before parenting), converts every Motor6D between direct body parts to a `BallSocketConstraint` limited to `RAGDOLL_JOINT_LIMIT` (the weapon motor stays rigid), copies each body part's CFrame so the death pose is kept, turns `CanQuery` and `CanTouch` off on every part (shots ignore corpses) and `CanCollide` on for body parts except the root, sets `RAGDOLL_DENSITY`, hands every part to the server with `SetNetworkOwner(nil)` (auto ownership would give it to the victim's client, which is then teleported out of simulation range and leaves the corpse frozen upright for everyone), gives it the victim's velocity plus `RAGDOLL_IMPULSE` away from the killer (forward when there is none: a perfectly still upright ragdoll sleeps on its feet), and parents it under `Workspace.Ragdolls`, where `Debris` removes it after `RAGDOLL_LIFETIME` (respawns would otherwise pile corpses up) and `clear()` empties the folder at match end. Bots go through the same path, and so does a player who resets mid-round (see Elimination). `_build(model)` is the pure conversion, checked by `Systems/RagdollTest.luau` against the NPC rig (run it in a play session's Server VM, see LeanSystem).
- `Systems/MapManager.luau`: clones map from `ServerStorage.Maps` into `Workspace.LoadedMap`, manages spawn points and the arena and lobby teleports. `spawnCFrameAwayFrom(exclude?)` returns the spawn point farthest from every live combatant (the `InRound` tag: Safe players and bots) except `exclude`; `teleportToArena(player)` uses it, so a spawn lands away from enemies. The choice is the pure `_pickSpawn(spawns, enemies)`: the index of the point whose nearest enemy is farthest, any point with no enemies, nil with no spawn points; covered by `Systems/SpawnPickTest.luau` (run in a play session's Server VM). Warns at `init()` if `ServerStorage.Maps` is missing or empty.
- `Systems/Store.luau`: coins, owned items and equipped choices, persisted in the `STORE_DATASTORE_NAME` DataStore keyed by `UserId`. The record is `{ version, coins, owned = { Weapons = {...}, Abilities = {...} }, equipped = { Weapons = name, Abilities = name }, settings = { sensitivity, keybinds = { Shoot, Shield, Dash, Sprint, Aim, Slide, Grapple } }, stats = { kills, deaths } }` (`stats` are lifetime totals across matches, merged as non-negative integers; `Store.addStat(player, key)` with a `STAT_KEYS` name bumps one and marks the wallet dirty, `RoundManager` calls it per player kill and per player death). On join it creates `leaderstats.Coins`, loads the record (`STORE_LOAD_RETRIES` attempts, `STORE_RETRY_DELAY` apart; a Studio session without API access gives up at once and runs session-only with one warning) and merges it with the catalog through `Store._merge`: every free item (`price == 0`) is owned, names the catalog no longer has are dropped, and an equipped name that isn't owned falls back to `VIEWMODEL_DEFAULT_WEAPON` or the first owned item. A failed load builds defaults and flags the wallet unsaveable so a bad read never overwrites a good save; coins earned before the load finishes are held and added afterwards. Saves go through `UpdateAsync` on `PlayerRemoving`, `BindToClose`, every `STORE_AUTOSAVE_INTERVAL` seconds (dirty wallets only) and right after a coin pack receipt. `addCoins(player, n)` is called by `RoundManager` per kill (`SHOP_COINS_PER_KILL`) and per win (`SHOP_COINS_PER_WIN`). `ShopPurchase(kind, name)` with `kind` `Weapons` or `Abilities` (`Catalog` kinds) deducts the item module's `price`, marks it owned and equips it. `ShopEquip(kind, name)` switches between owned items of either kind. Every change pushes `ShopState` to the owner. `equipped(player, kind)` is what `RoundManager` welds at spawn and what `AbilitySystem` checks before dashing. Coin packs are developer products: `MarketplaceService.ProcessReceipt` finds the `Items.Robux` module with that `productId`, grants its `coins`, saves, and returns `PurchaseGranted` only once the save succeeded (`NotProcessedYet` if the wallet isn't loaded or saveable, the product is unknown, or the save failed, rolling the coins back). `settings` is merged through `Shared/Settings.merge` on load and on every `SettingsUpdate(settings)` from the client (the merge is the validation), marked dirty and pushed back inside `ShopState`. The pure helpers `_merge`, `_purchase`, `_equip` and `_addStat` are covered by `Systems/StoreTest.luau`, run from the command bar with `require(game.ServerScriptService.Systems.StoreTest)()` (in a play session's Server VM if the Edit VM has a stale cache; `Systems/SettingsTest.luau` covers the settings merge the same way).
- `Systems/AbilitySystem.luau`: dash mechanic for safe players (Q key). Only acts when the player's equipped ability (`Store.equipped(player, "Abilities")`) is `Dash`; any other equipped ability is inert. Cooldown, duration and velocity come from `Abilities.params("Dash")`. The dash goes along `Humanoid.MoveDirection` (WASD, camera-relative, replicated), or forward when standing still. Phase-gated via `start()` / `stop()`: dash is rejected outside the active `Round` phase, so players cannot dash in the lobby or during the end freeze. `start()` also clears `lastDash` so cooldowns don't carry across matches. The dash is a `LinearVelocity` in plane mode (horizontal only) whose `MaxForce` is the assembly mass times `PUSH_MAX_ACCEL`: the force must stay finite, because an unlimited one fights the collision when the character meets a wall and the solver launches it (measured: 80 to 210 studs/s off the wall, spinning), and it must stay above roughly 2000 per unit of mass or a grounded humanoid holds the character in place.
- `Systems/GrappleSystem.luau`: the server side of the grapple (see Grapple). Validates `GrappleRequest(anchor)` (round active via `start()` / `stop()` alongside `CombatSystem`, `Safe`, shield down, no rope already out, `GRAPPLE_COOLDOWN` since the last release, anchor accepted by `GrappleMath.validAnchor`) and owns the rope: one `Beam` named `GrappleRope` in the character, from a `GrappleHand` attachment at the end of the right arm to a `GrappleAnchor` attachment under `Workspace.Terrain`. The Heartbeat step releases a rope when `GRAPPLE_MAX_TIME` passes, the shield goes up, the player is no longer `Safe` or the character is gone; `GrappleRelease` from the client and `stop()` release too. The cooldown counts from the release. Bots do not grapple.

### Client (`src/StarterPlayerScripts/`)

- `Main.client.luau`: bootstrap. Inits `AbilityHUDController`, `DashController`, `UIController`, `KillFeedController`, `KillConfirmController`, `CombatController`, `CombatFeedbackController`, `ChangeIndicatorController`, `ShopController`, `SettingsController`, `KillCamController`, `MovementController`, `GrappleController`, `SprintEffectController`, `ShiftLockController`, `MinimapController`, `SpectateController`, `SpawnController`, `MobileControlsController`, `TopBoardController`, `ScoreboardController` (in that order).
- Remotes that identify another combatant (`DamageDealt` victim, `DamageTaken` attacker, `ShotBlocked` other) carry a `Player` for players and the bot `Model` for bots. `KillFeed` carries names only; a bot's name is its generated model name (`ShadowKnight_27`).
- The camera is always the **stock Roblox classic camera with a free cursor**; there is no custom camera code outside the kill cam. `StarterPlayer.DevCameraOcclusionMode` is `Zoom` (set in `default.project.json`): the stock popper pulls the camera in front of any wall between it and the character, so the camera never sits behind geometry (Invisicam let it, and the aim ray then hit the wall behind the player). The client aim ray also starts at the character's depth along the camera ray rather than at the camera, so nothing between the camera and the player can become the aim point. `CameraMinZoomDistance` and `CameraMaxZoomDistance` are both 12.5 (also in `default.project.json`), so the scroll wheel cannot change the camera distance. During combat, `ShiftLockController` forces shift lock the way the stock PlayerModule does internally (`UserGameSettings.RotationType = CameraRelative`, `MouseBehavior = LockCenter` re-asserted right after the camera render step, `Humanoid.CameraOffset = SHIFTLOCK_CAMERA_OFFSET`), and releases all three when combat mode ends. The stock `CameraModule` no longer exposes its mouse lock controller (`PlayerModule:GetCameras()` returns `{}`), so it cannot be toggled through the PlayerModule. Shift's built-in mouse-lock toggle is unbound so it never fights the forced lock. While locked, the crosshair sits at the viewport center and aiming is a raycast from the camera through the center; otherwise the crosshair follows the mouse cursor and the ray goes through the cursor.
- `Controllers/MovementController.luau`: client-side movement extras, all gated on combat mode (`CombatController.isCombatActive()`), and the only writer of the camera FOV. **Sprint**: hold Shift while the shield is down: `WalkSpeed` to `SPRINT_WALKSPEED` and FOV eased `CAMERA_FOV` to `SPRINT_FOV` over `SPRINT_FOV_TWEEN_TIME`; the local character is client-simulated, and WalkSpeed is re-applied every frame because the server rewrites it on shield changes. **Aim**: hold the `Aim` key (default `4`) for FOV `AIM_FOV` over `AIM_FOV_TWEEN_TIME` (no speed change) and the settings' aim sensitivity as `MouseDeltaSensitivity` (1 whenever not aiming); aim wins over sprint for the FOV. **Double jump**: a second jump request while in `Freefall`, at least `DOUBLE_JUMP_DELAY` after leaving the ground, calls `Humanoid:ChangeState(Jumping)` once per airtime; resets on `Landed`. `SHIFTLOCK_CAMERA_OFFSET` is wider than the stock 1.75 so the character sits clear of the centered crosshair. **Movement animations** (not gated on combat): on character bind it preloads every clip with `ContentProvider:PreloadAsync` (in a spawned task, so the jump-state wiring doesn't wait), then loads the six `MOVEMENT_ANIMATIONS` (idle, forward, backward, left and right walks, run) on the humanoid's `Animator` at Movement priority, looping at near-zero weight. The preload matters: a track takes the asset's authored priority and loop flag when its data arrives, which on a live client is after `LoadAnimation` returns, so without it the authored values (several clips are exported as Action or Idle) silently replace what the script set. Studio has the assets cached and never shows this. Every frame the weights and playback speeds come from `Shared/MovementBlend` (shared with the bots' `BotAnimator`): the four walk weights from `MoveDirection` in root space, normalized to sum to the input magnitude; while sprinting the forward share goes to the run track instead; idle takes the rest, and all six drop to near zero while airborne so the stock fall shows. Walk playback speed is horizontal velocity over `MOVEMENT_ANIM_REFERENCE_SPEED`, the run's over `MOVEMENT_RUN_REFERENCE_SPEED`, weights ease over `MOVEMENT_ANIM_FADE` on the ground and over the shorter `MOVEMENT_AIR_FADE` while airborne or on the grapple (which counts as airborne even when dragged along the floor): the fade restarts every frame, which stretches it, and the ground fade left the run clip playing for about 0.4s after takeoff, at several times its speed on the grapple. Movement priority sits above the stock Animate script's Core walk, so no Animate changes are needed. Every frame a movement track that is not playing is played again at epsilon weight: applying the character's appearance shortly after a respawn stops every track on the Animator, and unlike the stock Animate script nothing else would restart ours. One-shots at Action priority: `JUMP_ANIMATION` on every `Jumping` state change (double jump included), and `playDashAnimation()` (called by `DashController` on a dash) plays the `DASH_ANIMATIONS` track that `MovementBlend.dashTrack` picks from the root-space move direction: Left or Right when the sideways component dominates, else Forward (a standing dash goes forward) or Backward. **Slide**: the `Slide` key (default C) while combat is active, the shield is down, the character is on the ground and moving, and `SLIDE_COOLDOWN` has passed since the last slide: the move direction at the press carries the character for `SLIDE_DURATION` through a `LinearVelocity` plane constraint on the root (`SlideVelocity`; the humanoid re-drives the velocity every physics step, so a plain write would not hold), easing from `SLIDE_SPEED` to `SAFE_WALKSPEED`, keys released or not, while `SLIDE_ANIMATION` plays at Action priority; jumping or leaving the ground ends it early and stops the clip.
- `Controllers/GrappleController.luau`: the grapple input and pull (see Grapple). `setHeld(on)` is public for a touch button; `isGrappling()`.
- `Controllers/SprintEffectController.luau`: cosmetic sprint speed lines. At init it builds a full-screen `SpeedLines` Frame in the `Game` ScreenGui holding `SPEED_LINE_COUNT` thin streak Frames (`SPEED_LINE_COLOR`, `SPEED_LINE_THICKNESS`), each at a random angle around the screen center with its bright end on the screen border and pointing inward, `SPEED_LINE_MIN_LENGTH..MAX_LENGTH` of the center-to-border distance long, with a `UIGradient` that fades toward the center. Every `RenderStepped` an intensity eases toward 1 while `MovementController.isSprinting()` and the root part's horizontal velocity is at least `SPEED_LINE_MIN_SPEED` (holding Shift against a wall or standing still shows nothing), else toward 0, over `SPEED_LINE_FADE_TIME`; streak transparency follows it down to `SPEED_LINE_MAX_TRANSPARENCY`, and each streak respawns at a new angle and length every 50..100% of `SPEED_LINE_LIFETIME` so the field flickers. The container is hidden, and nothing is touched, while the intensity is 0.
- `Controllers/SettingsController.luau`: the player's settings on this client. Holds the `Shared/Settings` record that arrives inside `ShopState`; `SettingsController.matches(input, action)` is what `CombatController` (`Shoot`, `Shield`), `DashController` (`Dash`) and `MovementController` (`Sprint`, `Aim`, `Slide`) test their `InputBegan` / `InputEnded` against instead of fixed keys. On every record change it rewrites the HUD key hints (`ShieldMeter` / `GunMeter` `BarBG.KeyHint`, `AbilityAction.KeyHint`) with `Settings.displayName`. The sensitivity is an aim multiplier: `MovementController` applies it as `UserInputService.MouseDeltaSensitivity` only while the Aim key is held and resets it to 1 otherwise, so outside aiming the stock camera turns on the player's own Roblox sensitivity (`UserGameSettings.MouseSensitivity` cannot be written by a LocalScript). The lobby `SETTINGS` modal (registered through `ShopController.registerModal`, so it shares the scrim and animations) is built from `ID_Objects.SettingRow` clones: one per action whose `Value` button opens the modal's `Confirm` overlay as a question (`CHANGE SHIELD KEYBIND?`, `Yes` / `No`); `Yes` keeps the overlay up over the rows reading `PRESS A KEY OR MOUSE BUTTON FOR SHIELD` with `No` relabelled `CANCEL`. A keyboard key binds through `UserInputService.InputBegan` (ignored when the GUI already took it, e.g. typed into a box) and a mouse button through the overlay's own `InputBegan` (ignored while the mouse is over `CANCEL`), so nothing clicked on the modal's other buttons can become the key; `CANCEL` or the modal closing cancels; a key already on another action is refused and the row keeps its key. The `AIM SENSITIVITY` row shows the template's `Input` TextBox instead of `Value`: `Minus` / `Plus` step by `SENSITIVITY_STEP`, and a typed number applies on focus loss through `Settings.parseSensitivity` (rounded to a step, clamped to `SENSITIVITY_MIN..MAX`; garbage reverts to the current value). Every accepted change sends `SettingsUpdate` at once. The keybind rows exist only when the device has a keyboard and a mouse; the sensitivity row and the button are there everywhere.
- `Controllers/MobileControlsController.luau`: touch stand-ins for the combat inputs. Binds the Studio-authored `Game.MobileControls` buttons (found by name anywhere under the frame) `Shoot`, `Shield` and `Dash` to `CombatController.tryShoot`, `CombatController.tryToggleShield` and `DashController.tryDash` (the public functions the mouse and keys call, with every gate inside them), and `Sprint` / `Aim` as toggles over `MovementController.setSprintHeld` / `setAimHeld` (held keys on a keyboard; a held touch button would need a third finger). A toggle that is on swaps its fill and label colors, and every toggle is forced off whenever the frame hides so nothing carries into the lobby or the next life. The frame shows only on a touch device without a keyboard while combat is active (local `Safe`, phase `Round`); the dash button additionally hides unless the equipped ability is Dash. Aiming needs nothing extra: shift lock is forced in combat, so a tapped shot goes through the screen center. Studio reports no touch, so to try it in a play session set the frame `Visible` from the client and click the buttons.
- `Controllers/TopBoardController.luau`: the in-match top kills board under the secondary status pill (`Game.TopBoard`, visible during `Round`). At init it clones `TOP_BOARD_SIZE` `ID_Objects.TopRow` rows into the board and, on every `MatchScores` attribute change, fills them from the `Top` attribute (rank, upper-cased name, `Kills_<name>`; the local player's name in `TOP_BOARD_SELF_COLOR`). The `Avatar` image is the `GetUserThumbnailAsync` headshot of the player's `UserId` or the bot model's `AvatarUserId` attribute, cached per name for the match (cleared when `Round` begins); a name with no id yet (a bot still loading its avatar, or dead) is looked up again `TOP_BOARD_AVATAR_RETRY` later.
- `Controllers/ScoreboardController.luau`: the Tab scoreboard (`Game.Scoreboard`, hidden by default; Tab toggles it, ignored when the GUI took the key, e.g. in chat). At init it disables the CoreGui `PlayerList` so Tab opens only this one. While open it rebuilds `ID_Objects.ScoreRow` clones in `Scoreboard.Rows` on every `MatchScores` attribute change and player join or leave: one row per name among the players, the models under `Workspace.Bots` and the `Kills_` / `Deaths_` attributes, sorted by kills, then fewer deaths, then name; the local player's name in `TOP_BOARD_SELF_COLOR`. Match numbers only; the lifetime totals are saved (see Store) but not shown.
- `Controllers/MinimapController.luau`: drives the Studio-authored `Game.Minimap` frame (`MINIMAP_*` tunables for the dots), visible while the phase is `Round` and the local player is `Safe` (a player waiting in the lobby sees no map). Every `RenderStepped` it places one dot per combatant (every player's character plus every model under `Workspace.Bots`) relative to the local player: the local player is always the center, the camera's horizontal look direction is up (so the map turns with the player), and `MINIMAP_RANGE` studs reach the edge; dots beyond that are hidden (players standing in the lobby). Dot colors: the local player is white, a character with a `PlayerShield` bubble is blue, one that fired within the last `MINIMAP_SHOT_FLASH` seconds is yellow (the server bumps a replicated `Shots` attribute on the shooter's character in `CombatSystem.shoot`), otherwise red.
- `Controllers/SpectateController.luau`: lobby-only spectating behind the `SpectateButton` in `Lobby.Buttons` (bound through `ShopController.bindLobbyButton`, so it hovers and presses like the other two). The `InRound`-tagged instances with a humanoid in `Workspace` (Safe players' characters and bot models) form a ring sorted by name. Clicking picks the first, closes any open modal (`ShopController.closeAll`), hides `Lobby.Buttons` and, every `RenderStepped`, keeps the camera `Custom` with that humanoid as `CameraSubject`: the stock camera orbits the target. While active the `Lobby.Spectate` bar is the only lobby UI: the target's name between `Prev` / `Next` buttons that walk the ring, and `Exit` (`BACK TO LOBBY`) under them. When the target loses the tag or leaves `Workspace` (eliminated, ragdolled, match over) it hands over to the next name in the ring; with none left, on `Exit`, or when the local state leaves `Lobby`, it restores the local humanoid, hides the bar and shows the buttons again if the state is still `Lobby`. While spectating the lobby buttons (`SpawnButton` included) are hidden, so the player leaves with `BACK TO LOBBY` before spawning.
- `Controllers/SpawnController.luau`: the lobby `SPAWN` button (`Lobby.Buttons.SpawnButton`, bound through `ShopController.bindLobbyButton`). It shows while the phase is `Round` (the whole `Buttons` frame already shows only in state `Lobby`) and reads `SPAWN`, or `SPAWN IN n` while `RESPAWN_DELAY` runs after a death (a `Safe` to `Lobby` change during `Round` starts the local countdown; a phase change resets it), during which clicks do nothing. A click sends `SpawnRequest` (no arguments) while the state is `Lobby` and the phase is `Round`; the server checks the same delay from its own, earlier clock, so a click the button allows is never refused for being early.
- `Controllers/KillCamController.luau`: on `KillFeed` where the local player is the victim and the killer is another player with a character (or a bot under `Workspace.Bots`), sets the camera `Scriptable`, eases it over `KILL_CAM_TWEEN_TIME` to `KILL_CAM_DISTANCE` studs in front of the killer's head (on the side the victim died on, `KILL_CAM_HEIGHT` up) looking at them, tracks the killer per frame for `KILL_CAM_TIME`, then restores `Custom` on the local humanoid. Ends early if the killer's character goes away. Client only: the server still teleports the victim to the lobby immediately, only the camera stays behind. `play(killerCharacter)` is public so it can be driven against a dummy rig in a solo playtest.
- `Controllers/UIController.luau`: reads phase/player-state remotes, renders RichText into `Game.StatusFrame.Status` (main announcements) and the `Game.SecondaryStatus` pill (`Secondary` + `Alive` chips). Scores come from the attributes on `ReplicatedStorage.MatchScores` (see `MatchScore`). During `Round`, Status reads `FIRST TO 20` (`KILL_TARGET`) until someone scores, then `<NAME> LEADS 12`, and the pill shows the timer (`5:00`, red below 30s) on the left and `KILLS 3/20` (the local player's kills against `KILL_TARGET`) on the right, in the `Alive` chip. In `Lobby` Status reads `WAITING FOR PLAYERS...` and the pill shows a single full-width `PLAYERS 4/2` line (lobby-state players plus planned bots over `MIN_PLAYERS`). At `End`, Status renders `<NAME> WINS!` for the first winner, or `MATCH ENDED` with no winner, and the pill is hidden.
- `Controllers/KillFeedController.luau`: listens to `KillFeed` remote, clones `Game.ID_Objects.KillData` into `Game.KillFeed` per kill and positions the rows itself (the feed has no layout object). Rows stack down from the feed's top edge, oldest first: a new kill slides in from the right below the others, and whenever a row leaves, the rows under it tween up one slot over `SHIFT_TIME`; `ROW_GAP` (fraction of the feed height) separates them. After `DISPLAY_TIME` a row fades while sliding fully off the right edge of the screen (`SLIDE_OUT_MARGIN` past its own width) and is destroyed; exceeding `MAX_ENTRIES` evicts the oldest the same way. Text is `"<Killer> shot <Victim>"` when there's a killer, `"<Victim> eliminated"` otherwise.
- `Controllers/KillConfirmController.luau`: pop-up notification ("ELIMINATED <Name>") shown to the killer only when `KillFeed` fires with `killerName == localPlayer.Name`. Clones `Game.ID_Objects.KillConfirm` into `Game` per kill. Each banner has its own independent lifecycle (expand → fade-in → 3s hold → fade-out → collapse): banners do **not** cancel each other. Concurrent kills stack: the newest sits at the template's authored position; older ones reflow by `STACK_DIRECTION` (-1 = upward) × `(height + STACK_GAP)` per slot. Soft cap `MAX_STACK = 5` evicts the oldest banner when exceeded; the evicted banner's coroutine bails on its next `clone.Parent` check after destroy. All stacking tunables are at the top of the file.
- `Controllers/DashController.luau`: sends `DashRequest` on Q, phase-gated to `Round`, state-gated to `Safe`, and only while `AbilityHUDController.equippedAbility()` is `Dash`. Resets `lastDash` to 0 the moment the client sees phase transition into `Round`, so stale cooldowns don't carry across matches.
- `Controllers/CombatController.luau`: shooting and shield input, and the source of truth for the shield and gun meters. On LMB, raycasts `Camera:ViewportPointToRay` at the mouse cursor out to `PISTOL_RANGE` (excluding the local character) to find the aim point and the part under it, then fires `ShootRequest(Head.Position, direction, aimPoint, hitPart?)`: client-side gated on state `Safe`, phase `Round`, shield not up, and the local `PISTOL_COOLDOWN` timer. On E, fires `ShieldRequest(true)` to raise (only when status is Ready) or `ShieldRequest(false)` to lower (only while Up). Listens to `ShieldChanged(status, duration, breaksInChain)` to drive `Game.Actions.Meters.ShieldMeter.BarBG.Fill`: full and draining to empty over `duration` while Up, empty and filling back up over `duration` while on Cooldown, full and static when Ready. `BarBG.EmptyOverlay` is visible only during Cooldown. `Game.Actions.Meters.GunMeter` has the same children: on every shot sent its `Fill` snaps empty and refills over `PISTOL_COOLDOWN` with `EmptyOverlay` visible until full; it resets to full on every phase change. The meters' parent (`Game.Actions`) is shown only while combat is active - local state `Safe` and phase `Round`. Exposes `ShotFired: BindableEvent.Event`, fired with the aim point whenever a shot is actually sent, consumed by `CombatFeedbackController` for the crosshair punch and the shooter's own tracer.
- `Controllers/CombatFeedbackController.luau`: purely cosmetic. Listens to `DamageDealt` (shooter side: throttled hit-confirm sound, batches damage into floating numbers above the victim's head via the `ReplicatedStorage.Assets.UI.DamageNumber` BillboardGui template), `DamageTaken` (victim side: vignette pulse, camera shake via `Humanoid.CameraOffset`, HP-threshold grunts at 75/50/25%, looping sizzle while taking damage), `KillFeed` (kill-confirm whoosh for a kill landed / convert-impact effect when eliminated), `ShotBlocked` (a sound for either party when a shield absorbs a shot), and `ShotTracer` (draws another combatant's tracer). Uses `Game.Vignette` and `Game.Crosshair` GuiObjects. Local-only sound IDs are stubbed (`""`): see the `SOUND_IDS` table at the top of the file when assets are ready. The gunshot and the three shield sounds (raise, lower, break) are played **server side** by `CombatSystem` (a `Sound` parented to the relevant head, so everyone hears them spatially); their IDs are `PISTOL_SHOT_SOUND`, `SHIELD_RAISE_SOUND`, `SHIELD_LOWER_SOUND` and `SHIELD_BREAK_SOUND` in Constants.
  - **Combat mode**: listens to both `PlayerStateChanged` and `RoundStateChanged` for the local player. Active iff `state == Safe AND phase == Round`. When active, hides the system cursor (`UserInputService.MouseIconEnabled = false`), shows `Game.Crosshair` and moves it to the mouse position every `RenderStepped`. When inactive, restores the cursor, hides the crosshair and resets it to idle. Damage shake writes `Humanoid.CameraOffset` each frame while decaying, additive on top of `ShiftLockController.baseCameraOffset()` (the shoulder offset while locked, zero otherwise), and settles back to that base.
  - **Tracer**: client-drawn. A neon segment `PISTOL_TRACER_LENGTH` long flies at `PISTOL_TRACER_SPEED` from the shooter's muzzle to the end point, stepped on `RenderStepped`, then a `PISTOL_IMPACT_PARTICLES` spark burst plays where it lands. The muzzle is an `Attachment` (or part) named `Muzzle` anywhere in `EquippedWeapon`, else the weapon's primary part, else the head. The local shooter draws theirs on `CombatController.ShotFired` to their own aim point; everyone else draws on `ShotTracer`.
  - **Crosshair**: four `Arm` Frames built at `init()` inside the Studio `Game.Crosshair` Frame (whose own background and stroke are disabled; it is only the mouse-following anchor). Idle by default, punched (the anchor's size tween spreads the arms, and each arm's color tweens; reverses automatically) on `CombatController.ShotFired`. Arm length, thickness and colors are the `CROSSHAIR_*` tunables at the top of the file.

### Character (`src/StarterCharacterScripts/`)

- `Health.client.luau`: empty override of Roblox's default Health script. Disables passive HP regen so damage persists between encounters.

### Shared (`src/ReplicatedStorage/`)

- `Shared/Constants.luau`: all tunables (match timing, kill target, respawn delay and spawn protection, pistol/shield numbers, movement, shop economy and DataStore timing, state and phase strings, UI colors, shield status strings, end reasons). Per-item tunables (price, stats, ability params, weapon grip) live in the item modules under `Items` instead.
- `Shared/Catalog.luau`: the item catalog. Every ModuleScript under `ReplicatedStorage.Items.<Kind>.<Name>` (kinds `Weapons`, `Abilities`, `Robux`; source under `src/ReplicatedStorage/Items/<Kind>/<Name>/init.luau`) is one item returning `{ displayName, price?, description?, stats? = { { label, value }, ... }, params? (abilities), grip? (weapons), gamePassId? / productId? + coins? (Robux) }`. Studio-authored children ride along inside the module (every folder has `ignoreUnknownInstances`): a weapon's `Model`, an ability's or Robux item's `Icon` ImageLabel. `Catalog.items(kind)` (sorted by price then name), `Catalog.get(kind, name)`, `Catalog.model(kind, name)`, `Catalog.icon(kind, name)`, `Catalog.free(kind)`. Read once on first use; a module that errors or doesn't return a table is warned about and skipped.
- `Shared/Settings.luau`: the settings record and its validation, used by both sides. Keys are stored by name (`Enum.KeyCode` names or `MouseButton1/2/3`; `Escape` and `Unknown` are reserved). `Settings.merge(raw)` returns a valid record from anything: defaults from `DEFAULT_KEYBINDS` / `SENSITIVITY_DEFAULT`, unknown actions dropped, bad key names fall back per action, two actions on one key reset the whole set, sensitivity clamped. `Settings.parseSensitivity(raw)` turns typed text or a stepped number into a sensitivity rounded to `SENSITIVITY_STEP` and clamped, or nil for a non-number. `displayName` (`LMB`, `RMB`, `LSHIFT`, `Q`), `inputMatches(input, name)` and `keyNameOf(input)` are the input-side helpers. Checked by `Systems/SettingsTest.luau`.
- `Shared/MovementBlend.luau`: the pure movement animation blend used by `MovementController` (client) and `BotAnimator` (server): `weights(localMove, amount, grounded, sprinting)` and `playback(name, horizontalSpeed)`. Checked by `Systems/MovementBlendTest.luau`.
- `Shared/GrappleMath.luau`: the pure grapple math used by both sides: `validAnchor(rootPosition, anchor, slack)`, `pullSpeed(startSpeed, elapsed, distance)` and `clampSpeed(velocity, maxSpeed)`. Checked by `Systems/GrappleTest.luau`.
- `Shared/Types.luau`: Luau type aliases: `PlayerStateName` (`"Lobby" | "Safe"`), `RoundPhase` (`"Lobby" | "Round" | "End"`), `EndReason` (`"KillTarget" | "TimeUp" | "Aborted"`), `RoundEndExtra`.
- `Shared/Abilities.luau`: thin wrapper over the catalog's `Abilities` kind. `Abilities.get(id)` resolves an item into an `AbilityDef` (`displayName` from the module, icon image and color from its `Icon` child), `Abilities.params(id)` returns the module's `params` (`DEFAULT_PARAMS` when absent). Only Dash has behavior; other abilities can be bought and equipped but are inert.

### Remotes (`ReplicatedStorage.Remotes`)

The `Remotes` folder lives in Studio (not Rojo source); it is preserved across syncs because `ReplicatedStorage` has `ignoreUnknownInstances: true`. Several remotes are **auto-created** by their owning system if missing (the `ensureRemote` pattern), so you don't have to author them in Studio.

- `RoundStateChanged` (RemoteEvent): server broadcasts `(phase, duration?, extra?)` with `phase` one of `Lobby`, `Round`, `End`. During `Lobby` and `Round`, `extra` is `nil`. At `End`, `extra` is `{ winners = { name }, reason }` with `reason` one of `KillTarget`, `TimeUp`, `Aborted`: `winners` holds the single top scorer, and is empty when `reason == "Aborted"` or nobody scored.
- `SpawnRequest` (RemoteEvent): client → server, no arguments. Accepted when the phase is `Round`, the player is `Lobby`, their character is alive and `RESPAWN_DELAY` has passed since their last death; anything else is ignored. Auto-created by `RoundManager.init()`.
- `PlayerStateChanged` (RemoteEvent): server broadcasts `(player, state)`.
- `DashRequest` (RemoteEvent): client → server.
- `ShootRequest` (RemoteEvent): client → server `(origin: Vector3, direction: Vector3, aimPoint: Vector3, hitPart: BasePart?)`. `origin` is the client's Head position, `aimPoint` where the crosshair ray ended and `hitPart` what it hit (nil on a miss). Server rejects if `origin` is more than `PISTOL_ORIGIN_TOLERANCE` studs from the server-side head, if `direction` isn't a finite non-zero vector, if the round isn't active, if the shooter isn't `Safe`, if their shield is up, or if they're still on `PISTOL_COOLDOWN`. Auto-created by `CombatSystem.init()`.
- `ShieldRequest` (RemoteEvent): client → server `(raise: boolean)`. `true` raises (rejected if already up, on cooldown, round inactive, or not `Safe`); `false` lowers manually and starts the cooldown. Auto-created by `CombatSystem.init()`.
- `ShieldChanged` (RemoteEvent): server → owning client only `(status, duration, breaksInChain)`. `status` is one of `Constants.SHIELD_UP` / `SHIELD_COOLDOWN_STATUS` / `SHIELD_READY`; `duration` is how long that status lasts (0 for Ready). Sent on every transition (raise, natural expiry, manual lower, break, cooldown ending) and once each on `CombatSystem.start()` / `stop()` as Ready. Auto-created by `CombatSystem.init()`.
- `ShotBlocked` (RemoteEvent): server → both parties `(otherPlayer: Player)`, sent when a shield absorbs a shot: to the shooter with the victim, to the victim with the shooter. Auto-created by `CombatSystem.init()`.
- `DamageDealt` (RemoteEvent): server → shooter `(victim: Player | Model, dmg, victimHP)` on a landed, unblocked shot. `victimHP` is the HP after the shot (0 on elimination). Auto-created by `CombatSystem.init()`.
- `DamageTaken` (RemoteEvent): server → victim `(attacker: (Player | Model)?, dmg, currentHP)`, same moment as `DamageDealt`. Auto-created by `CombatSystem.init()`.
- `ShotTracer` (RemoteEvent): server → every client except the shooter `(shooter: Model, endPoint: Vector3)` on every accepted shot; the shooter draws their own tracer on input. Auto-created by `CombatSystem.init()`.
- `GrappleRequest` (RemoteEvent): client → server `(anchor: Vector3)`; `GrappleRelease` (RemoteEvent): client → server, no arguments. Both auto-created by `GrappleSystem.init()`.
- `KillFeed` (RemoteEvent): server broadcasts `(killerName?, victimName)` per elimination. Auto-created by `RoundManager.init()`.
- `ShopState` (RemoteEvent): server → owning client `({ coins, owned = { [kind] = { name, ... } }, equipped = { [kind] = name }, settings })` once the record is loaded and after every coin or item change. `ShopController` renders it; `AbilityHUDController` reads `equipped.Abilities` from it, `SettingsController` reads `settings`. The client also fires it with no arguments to ask for a fresh copy (the join-time push can beat the controller). Auto-created by `Store.init()`.
- `SettingsUpdate` (RemoteEvent): client → server `(settings)`, the whole record; the server keeps `Settings.merge(settings)` and pushes `ShopState`. Auto-created by `Store.init()`.
- `ShopPurchase` (RemoteEvent): client → server `(kind, name)`; `ShopEquip` (RemoteEvent): client → server `(kind, name)`. `kind` is a `Catalog` kind (`Weapons` / `Abilities`); validated against the catalog, ownership and coin balance. Auto-created by `Store.init()`.
- `FireRequest`, `FuelChanged`, `InfectionProgress`: no longer used by any active system; don't create or reference them (kept only to avoid Studio-side cleanup on old saves).

### GUI structure (`PlayerGui.Game`, a ScreenGui authored in Studio)

`ResetOnSpawn = false` (like `Lobby`): controllers resolve this ScreenGui once and build into it (the crosshair arms, kill feed rows), so it must survive respawns.

- `StatusFrame.Status` (TextLabel): main HUD line. `WAITING FOR PLAYERS...` in the lobby, `FIRST TO 20` then `<NAME> LEADS n` during the match, `<NAME> WINS!` (or `MATCH ENDED`) at end. RichText, all uppercase, no text stroke (flat like the rest of the top bar).
- `StatusFrame.Accent` (Frame): thin orange line under the headline, faded at both ends by a `UIGradient`. Static, no script touches it.
- `SecondaryStatus` (Frame): dark square-cornered band under the headline. `UIController` hides it when there is nothing to show (End phase). Children: `Secondary` (TextLabel, left chip: timer during `Round`, the whole line in every other phase, stretched to full width), `Alive` (TextLabel, right chip: `KILLS n/20`, the local player's kills against `KILL_TARGET`, visible only during `Round`), `Divider` (Frame, visible only with `Alive`). If `Alive` is missing, `UIController` falls back to one string in `Secondary` joined by ` | `.
- `TopBoard` (Frame): transparent, centered directly under `SecondaryStatus`, hidden by default, a vertical `UIListLayout` that `TopBoardController` fills with `ID_Objects.TopRow` clones (dark slabs in the pill's style: round `Avatar` ImageLabel, `Rank`, `Name`, `Kills` TextLabels). Shown during `Round` only.
- `Scoreboard` (Frame): centered dark slab (1.5:1 aspect), hidden by default, `ZIndex 5`: `Accent` bar, `Title`, a `Header` row (`Name`, `Kills`, `Deaths` labels in orange) and `Rows`, a ScrollingFrame with a vertical `UIListLayout` and automatic canvas that `ScoreboardController` fills with `ID_Objects.ScoreRow` clones (`Name`, `Kills`, `Deaths` TextLabels).
- `KillFeed` (Frame, no layout object): pinned top-right; kill feed rows are parented here with `AnchorPoint 1, 0` and positions set by `KillFeedController`. Rows hang from its top edge, so moving the frame moves the whole stack and its height only matters for the row template's scale. `ClipsDescendants` must stay off so rows can slide past its edge.
- `ID_Objects.KillData` (Frame): row template cloned per kill into `KillFeed`. Children: `Strip` (Frame, dark backing faded out leftward by a `UIGradient`) and `Label` (TextLabel, RichText, right-aligned, with a `UIStroke`). `KillFeedController` fades `Label` text, its stroke and `Strip` together. Hidden by default; `Visible = true` set on the clone.
- `ID_Objects.KillConfirm` (Frame): kill-confirm banner template, bottom-center, `ClipsDescendants = true` so its contents stay hidden while it is collapsed. `AnchorPoint` must stay `0, 0`: the expand/collapse tween grows it from its left edge. Children: `Title` (TextLabel with a `UIStroke`, both faded by `KillConfirmController`) and `Accent` (Frame, static).
- `Actions` (Frame, horizontal UIListLayout, right-aligned): the bottom-right HUD cluster. Anchored `1, 1` with a `UIAspectRatioConstraint` and a `UISizeConstraint` minimum, so the tile and meters scale as one unit; children are sized in scale against it. Shown only while combat is active for the local player. Children: `AbilityAction` (see below) and `Meters` (Frame, vertical UIListLayout) holding `ShieldMeter` and `GunMeter`, each with static `BarBG.Label` text and a `BarBG.KeyHint` that `SettingsController` keeps equal to the bound key (the meters' `UIShadow`s are disabled and the meter frames themselves are transparent, so each bar is a flat slab with only `BarBG` drawn and no dark rim; the labels keep their text strokes and the `AbilityAction` tile keeps its `UIShadow`), `BarBG.Fill` (sized 0..1 by `CombatController`: shield charge / pistol cooldown) and `BarBG.EmptyOverlay` (visible while that meter is refilling from a cooldown).
- `Minimap` (Frame): bottom-left square (a `UIAspectRatioConstraint` keeps it 1:1 against its height), flat dark slab, hidden by default. `MinimapController` shows it during `Round` and parents one dot `Frame` per combatant to it; keep `ClipsDescendants` on so dots never draw outside the slab.
- `SpeedLines` (Frame): built in code by `SprintEffectController` (not authored in Studio): full-screen, `ClipsDescendants`, holding the streak Frames; hidden unless sprinting.
- `Vignette` (Frame): full-screen damage overlay; `BackgroundTransparency` is tweened by `CombatFeedbackController` on every damage tick taken.
- `Crosshair` (Frame): anchor for the crosshair that follows the mouse cursor during combat (needs `AnchorPoint = 0.5, 0.5`). `CombatFeedbackController` makes it transparent, disables its `UIStroke`, and builds four orange `Arm` Frames inside it; punched (size + color tween) on every shot fired.
- `Actions.AbilityAction` (Frame): HUD tile for the equipped ability, left of the meters. Children: `AbilityIcon` (ImageLabel, image and color copied from the item module's `Icon` child), `AbilityTitle` (TextLabel, set to the module's `displayName`), `KeyHint` (TextLabel, kept equal to the Dash keybind by `SettingsController`), `Accent` (Frame, static), `Overlay` (GuiObject swept 1→0 height by `AbilityHUDController.triggerCooldown` across the ability's cooldown). Shown on the same rule as the meters: local player `Safe` and phase `Round`, and only once `ShopState` has named an equipped ability.
- `MobileControls` (Frame): right side, well above `Actions`, hidden by default; a bottom-aligned vertical stack of two right-aligned rows: `Top` with the `Aim` and `Sprint` toggles, `Bottom` with `Dash`, `Shield`, `Shoot`. All are round TextButtons (1:1 aspect, circular `UICorner`, plain label text, no strokes). `MobileControlsController` resolves them by name, toggles visibility and swaps a toggle's colors while it is on.
- `ChangeIndicator` (Frame): elimination banner. Children: `Title` (TextLabel, set to "ELIMINATED") and `UpdatedInfo` (TextLabel, set to "PRESS SPAWN"). Played by `ChangeIndicatorController` on every death of the local player during a match (the state leaves `Safe` while the phase is `Round`).

### Lobby GUI (`PlayerGui.Lobby`, a ScreenGui authored in Studio)

`ResetOnSpawn = false`, so controllers bind to it once. `IgnoreGuiInset = true`, so the scrim covers the Roblox top bar too.

- `Buttons` (Frame): transparent, on the left edge and centered on the screen's y axis (`AnchorPoint 0, 0.5`, the minimap's width and 1:1 aspect), with a left-aligned vertical `UIListLayout`, holding `SpawnButton` (`LayoutOrder 0`, first; hidden by default, shown by `SpawnController` during a match), `ShopButton`, `InventoryButton`, `SettingsButton` and `SpectateButton` (TextButtons; the last three are clones of the shop button driven by `SettingsController`, `SpectateController` and, for `SpawnButton`, `SpawnController`): native dark panels with a `UIScale` child, a horizontal `UIGradient` whose transparency runs solid on the left to mostly clear at the right edge (the hover fade multiplies with it), an `Accent` bar outside the left edge, left-aligned text and a `UIPadding` of about 12% sides / 18% top and bottom. Each button is `Size = 1, 0.22` of the frame (full width, 22% of the square's height; no aspect constraint); with five buttons the list is taller than the frame and overflows it evenly above and below (the frame does not clip). `Controllers/ShopController.luau` tweens `BackgroundTransparency` and the width (`HOVER_WIDTH` 108% on hover, `PRESS_WIDTH` on press) for feedback, so the button keeps its height and left edge and grows to the right; `ShopController.bindLobbyButton` is public for the same look elsewhere, and a button that carries a `UIAspectRatioConstraint` (the spectate row) scales its `UIScale` as a whole instead and opens the matching modal on click; opening one modal closes the other, and a modal closes only through its `Close` button (or the lobby UI hiding when the player spawns). The whole `Buttons` frame is visible only while the local player's state is `Lobby` (any open modal closes when it hides): it disappears when the player spawns into the arena, stays gone through the match-end freeze, and returns with the teleport back to the lobby, or immediately on elimination. `SpawnButton` additionally shows only while the phase is `Round`.
- `Scrim` (TextButton), `ShopModal` / `InventoryModal` (Frame) and the `ID_Objects` templates: all authored in Studio, in the lobby buttons' own style (flat dark warm slabs, sharp corners, no strokes, heavy italic type, one accent color per modal: orange for the shop, green for the inventory). `ShopController.init()` only resolves them by name and wires behavior; it reads each modal's accent from its `Accent` bar, its text color from `Title`, its dim color from `Close` and its panel color from the frame, so restyling in Studio flows through. ## Match Flow

`Lobby (waiting) → Round (the match, 300s) → End (3s arena freeze + 5s results = 8s) → Lobby`

`gameLoop` broadcasts `Lobby`, waits until `enoughPlayers()` (at least one real player, and players plus `BotSystem.plannedCount()` reaching `MIN_PLAYERS`), then loads a random map **before** the match starts. If the map fails to load (no `ServerStorage.Maps`, or it's empty), it warns, waits 5s and tries again, staying in `Lobby`.

**Round phase** (`ROUND_TIME = 300s`, `runMatch`): `MatchScore.reset()` clears the scores, the last-death times are cleared, then `CombatSystem.start()`, `AbilitySystem.start()`, `GrappleSystem.start()`, `BotSystem.spawn()` and `BotSystem.start()` run and `RoundStateChanged(PHASE_ROUND, ROUND_TIME)` is broadcast. Bots spawn at once. **Players start the match in the lobby** (state `Lobby`) and enter the arena with the lobby `SPAWN` button (`SpawnRequest`), late joiners included. The loop checks every 0.25s: it ends with `REASON_ABORTED` (winners empty) when players plus planned bots no longer satisfy `enoughPlayers()`, with `REASON_KILL_TARGET` as soon as `MatchScore.targetReached()` (a combatant has `KILL_TARGET` = 20 kills), and with `REASON_TIME_UP` when the timer runs out. A match with every real player sitting in the lobby still runs: the bots fight it out. The winner (`winnerNames()`) is the single top scorer, player or bot, by `MatchScore.leader()`; nobody wins when no kill was scored. A player winner gets `SHOP_COINS_PER_WIN`; a bot winner only gets the banner.

**Spawning** (`spawnIntoArena`, from `SpawnRequest`): accepted when the phase is `Round`, the player is `Lobby`, their character is alive, and `RESPAWN_DELAY` (3s, the kill cam's length) has passed since their last death. It then calls `CombatSystem.revive(char)`, `setSafe` (state `Safe`, walk speed, third-person weapon), `MapManager.teleportToArena` (the spawn point farthest from every live combatant) and `CombatSystem.protect(char)` (spawn protection).

**End phase** is a single 8-second window split server-side into two halves:
1. **Arena freeze (`END_DELAY_TIME = 3s`)**: `CombatSystem.stop()`, `AbilitySystem.stop()`, `GrappleSystem.stop()` and `BotSystem.stop()` run first (this strips every `PlayerShield` bubble), then every character's third-person weapon is detached, then every character gets an invisible `ForceField` named `RoundEndForceField` (belt-and-suspenders invincibility against any in-flight shot), and `RoundStateChanged(PHASE_END, END_DELAY_TIME + END_TIME, { winners, reason })` is broadcast **immediately**. Players still in the arena stand where they are, but combat mode deactivates client-side (phase ≠ `Round`) so the crosshair hides and the meters disappear. The single phase broadcast covers both halves so the End-phase timer reads correctly on the client.
2. **Results (`END_TIME = 5s`)**: players are healed to MaxHealth, `RoundEndForceField`s are stripped, everyone is teleported to the lobby and set to `STATE_LOBBY`, the bots are despawned, the ragdolls are cleared and the map is unloaded. The winner banner remains visible in the lobby for the remaining 5s before the next `gameLoop` iteration broadcasts `PHASE_LOBBY`.

`endRound(reason, winners)` is the function that orchestrates this: it pays the player winners → stops systems (Combat, Ability, Grapple, Bot) → detaches weapons → adds ForceFields → broadcasts `PHASE_END` (with the full 8s duration) → `task.wait(END_DELAY_TIME)` → heals + strips ForceFields + `setLobby` + teleports → despawns bots → clears ragdolls → unloads map → `task.wait(END_TIME)`.

Solo play needs nothing special: with `BOTS_ENABLED` and `BOT_COUNT = 5` one real player plus the bots satisfies `MIN_PLAYERS`. Set `BOTS_ENABLED = false` to play without them.

## Pistol

Hitscan, third-person aiming at the mouse cursor, one press per shot (no hold-to-fire).

- **Client**: on LMB, `CombatController` raycasts `Camera:ViewportPointToRay` at the mouse cursor out to `PISTOL_RANGE`, excluding the local character; the aim point is the hit position or the ray's far end. `direction = (aimPoint - Head.Position).Unit`, sent as `ShootRequest(Head.Position, direction, aimPoint, hitPart?)`. Client-side gates: state `Safe`, phase `Round`, shield not up, local `PISTOL_COOLDOWN` timer elapsed.
- **Server** (`CombatSystem.shoot`): re-validates everything the client already checked, plus `PISTOL_ORIGIN_TOLERANCE` (rejects if the claimed origin is too far from the server-side head) and re-normalizes/validates `direction` as a finite, non-zero vector. Then the **hit claim**: if `hitPart` belongs to a live combatant other than the shooter, `aimPoint` is within `PISTOL_RANGE` and within half the part's diagonal plus `PISTOL_HIT_TOLERANCE` studs of the part's server position, and a raycast from `origin` to `aimPoint` (excluding shooter and victim) hits nothing, that combatant is the victim and `aimPoint` the end point. The shooter's screen decides, so lag and camera-vs-head parallax don't eat hits; the tolerance bounds what a forged claim can reach to roughly what lag already allows. Any failed check, or no claim, falls back to raycasting `origin → direction * PISTOL_RANGE`, excluding the shooter's character.
- **Hitboxes**: `prepareHitbox` turns `CanQuery` off on every accessory part of every combatant, so hats, hair and the welded weapon never count. Body parts and the `PlayerShield` bubble are the only things a shot can land on.
- **Damage**: `PISTOL_DAMAGE` (100, one shot eliminates) applied only on a direct hit against another `Safe` player. A hit against a raised shield calls `breakShield` instead of dealing damage (see Shield below).
- **Tracer**: on every accepted shot (hit or miss), the server fires `ShotTracer(shooter, endPoint)` to every client except the shooter; the shooter's own client drew its tracer on input. Each client animates the segment from the muzzle to the end point and sparks on arrival (see `CombatFeedbackController`). Nothing tracer-related is created on the server.
- **Cooldown**: `PISTOL_COOLDOWN` (1.0s) between shots, checked server-side with `PISTOL_COOLDOWN_TOLERANCE` (0.05s) slack for network jitter.

## Shield

Raise it with E; it blocks exactly one shot, then breaks.

- **Raising**: welds a `Part` named `PlayerShield` to the root part (a `SHIELD_SIZE`-stud ball, `Material = ForceField`, `SHIELD_COLOR`, `SHIELD_TRANSPARENCY`, no collision, massless, `CanQuery` on so shots hit the bubble and resolve to its owner). The bubble pops in: it spawns at `SHIELD_RAISE_FX_START` scale and fully opaque, then tweens (Back out) to full size and `SHIELD_TRANSPARENCY` over `SHIELD_RAISE_FX_TIME`. Plays `SHIELD_RAISE_SOUND` at the head, and sets `Humanoid.WalkSpeed` to `SHIELD_WALKSPEED` (12, down from `SAFE_WALKSPEED` 16). Rejected if already up, on cooldown, the round isn't active, or the player isn't `Safe`. While the shield is up the player cannot shoot: the server rejects `ShootRequest` and the client doesn't even send it.
- **Duration: shrinking re-raise**: a freshly raised shield lasts `SHIELD_DURATIONS[1]` (1.0s). Each time it's *broken* by an incoming shot (not lowered manually, not expired naturally), `breaksInChain` increments and the next raise uses `SHIELD_DURATIONS[1 + breaksInChain]` (clamped to the array, 0.5s after one break, 0.25s after two or more). The chain resets to 0 breaks once `os.clock() - lastBreakAt > SHIELD_CHAIN_RESET` (5.0s), so pressure only stays cheap if the defender keeps re-raising fast; a gap resets them to the full 1s shield.
- **Natural expiry or manual lower**: either one removes the bubble (leaving an anchored `ShieldLowerFx` copy that shrinks to `SHIELD_LOWER_FX_SCALE` and fades over `SHIELD_LOWER_FX_TIME`), plays `SHIELD_LOWER_SOUND`, restores `SAFE_WALKSPEED`, and starts `SHIELD_COOLDOWN` (3.0s) before the player can raise again: `ShieldChanged` fires `SHIELD_COOLDOWN_STATUS` immediately, then `SHIELD_READY` once the cooldown elapses.
- **Break** (a landed shot hits a raised shield): the bubble is removed immediately and replaced by a short anchored `ShieldBreakFx` copy that swells by `SHIELD_BREAK_FX_SCALE` and fades over `SHIELD_BREAK_FX_TIME`, emits `SHIELD_BREAK_PARTICLES` cyan shards from a `ParticleEmitter`, and drops a Neon `ShieldBreakRing` cylinder at the owner's feet that expands to `SHIELD_BREAK_RING_SIZE` and fades over `SHIELD_BREAK_RING_TIME`, `SHIELD_BREAK_SOUND` plays at the head, `breaksInChain += 1`, `lastBreakAt = now`, and, critically, there is **no cooldown**. `ShieldChanged` fires `SHIELD_READY` right away, so the player can re-raise on the very next input, just with the shorter duration from the chain. `ShotBlocked` fires to both the shooter and the (former) shield holder.
- The Heartbeat `step` in `CombatSystem` is what actually expires an up shield past `expiresAt` and clears a cooldown past `cooldownUntil`: both paths funnel through `lowerShield`/status broadcasts so the client meter always matches server state.

## Grapple

Built in for every player, on the `Grapple` key (default right click; `Aim` defaults to `4`), held: the rope lives while the key is down. One rope, one anchor.

- **Fire**: during `Round`, shield down, `GRAPPLE_COOLDOWN` since the last release. The aim is the pistol's (`CombatController.getAim`). The part under the crosshair must be under `Workspace.LoadedMap` and the point within `GRAPPLE_RANGE` of the root and farther than `GRAPPLE_ARRIVE_DISTANCE`; players, bots, shields and ragdolls are not anchors. A miss does nothing and costs no cooldown.
- **Pull** (client, the character is client-simulated): the humanoid is put in `Freefall` and a `LinearVelocity` named `GrappleVelocity` on the root drives the whole velocity toward the anchor, so gravity is overridden while attached. The speed is `GrappleMath.pullSpeed`: from the speed already carried toward the anchor it ramps by `GRAPPLE_ACCEL` up to `GRAPPLE_SPEED`, and over the last studs it brakes (`GRAPPLE_BRAKE_RATE`) to `GRAPPLE_ARRIVE_SPEED`, so the character never meets the wall at full speed. `MaxForce` is finite (`PUSH_MAX_ACCEL`, see AbilitySystem), so geometry in the way stops the character.
- **Steering**: while attached, `GrappleMath.steer` adds up to `GRAPPLE_STEER_SPEED` across the rope (never along it, so the distance to the anchor always shrinks and the pull still arrives): sideways from `Humanoid.MoveDirection` along the camera's right vector (A/D or the thumbstick), up while jump is held, down while the `Slide` key is held. Jump held is read from `Humanoid.Jump`; `JumpRequest` fires with gaps of up to half a second while held. `MovementController` skips the double jump and the slide while `GrappleController.isGrappling()`.
- **Release**: within `GRAPPLE_ARRIVE_DISTANCE` of the anchor, the key coming up, the shield going up, combat ending, `GRAPPLE_MAX_TIME`, or a stall (slower than `GRAPPLE_STALL_SPEED` for `GRAPPLE_STALL_TIME`: something is in the way). The velocity is kept, capped at `GRAPPLE_SPEED`. A rope that let go on its own needs a new press; a key still held does not fire again.
- **Rope**: made by the server so it replicates; the owner sees it one network hop after the pull starts.
- Shooting works during the pull.

## Elimination

Players are **never killed** in the Roblox sense, and a death does not end the match. When a `Safe` player's HP reaches 0 from a landed shot:
- HP is restored to `MaxHealth`.
- `CombatSystem.PlayerEliminated` fires `(victim, killer?)`.
- `RoundManager.onPlayerEliminated`, gated to `currentPhase == PHASE_ROUND`, broadcasts `KillFeed(killerName?, victimName)`, adds one kill to the killer's score (`MatchScore.addKill`; a death with no killer scores for nobody) and one death to the victim's (`MatchScore.addDeath`), gives a player killer `SHOP_COINS_PER_KILL` and a lifetime kill, a player victim a lifetime death (`Store.addStat`), spawns the ragdoll corpse at the death spot (`RagdollSystem.spawn`, removed after `RAGDOLL_LIFETIME`), records the victim's death time, then sets the victim to `STATE_LOBBY` and teleports them to the lobby. A bot victim is destroyed through `BotSystem.remove` and comes back after `RESPAWN_DELAY`.
- A player spawns back in with the `SPAWN` button once `RESPAWN_DELAY` has passed (see Match Flow); while waiting they can shop, change settings or spectate. The victim's client plays the kill cam and the `ChangeIndicator` banner (`PRESS SPAWN`).
- `Humanoid.BreakJointsOnDeath` is set `false` on every spawn so a 0-HP frame never triggers ragdoll or a death animation.
- A player who dies for real while `Safe` (a reset, or anything else that zeroes the humanoid) is handled by the humanoid's `Died` connection made in `onCharacterAdded`. During `Round` it goes through `onPlayerEliminated(char, nil)`: kill feed reads `"<Victim> eliminated"`, a ragdoll is left, state flips to `Lobby`, nobody scores. In any other phase it only flips the state to `Lobby`. Every death, in any phase, is followed by `player:LoadCharacter()` at once, so a dead body never lies stiff waiting for the respawn timer (in the arena the ragdoll clone is the only body left behind), and the new character spawns in the lobby, since every new character starts there (the arena is entered with `SpawnRequest`). Roblox does not respawn a second time after the manual load.

`killerName` is always present for a pistol elimination; it's only `nil` for a reset, and `KillFeedController` then uses its no-killer text.

## Visual identity

- **Third-person weapon**: `RoundManager.setSafe` welds (through `Systems/WeaponModel.luau`) a clone of `Catalog.model("Weapons", Store.equipped(player, "Weapons"))` (the `Pistol` by default: `VIEWMODEL_DEFAULT_WEAPON` is the free weapon everyone owns; named `EquippedWeapon`) onto the character's right arm via a `Motor6D`, using the grip `CFrame` and motor name read from the matching rig under `ReplicatedStorage.ThirdPersonRigs`. Without a rig it uses the item module's `grip` (identity if absent) + `"Weapon"`. Every other part in the model is welded to the primary part with its authored offset, so a weapon authored as loose parts (the Pistol) holds together. Convention: the weapon's forward axis runs down the arm's -Y, its top faces the arm's -Z, and the grip sits about 0.72 studs below the arm center. `setLobby` and match end both detach it. Bots carry the default pistol the same way.
- **Shield**: the cyan `PlayerShield` bubble is the only visual: see Shield above. No outline/highlight system exists in this mode (there's no "who's the burner" to call out; everyone looks the same).

## Map Authoring

Maps live in `ServerStorage.Maps` (each is a `Model`). At runtime they are cloned into `Workspace.LoadedMap` (a Folder created on demand). `MapManager.unloadMap()` destroys the whole folder, so even if the `currentMap` reference is lost no orphan parts can survive.

Required structure inside each map Model:
- `SpawnPoints/` folder containing `BasePart`s named `SpawnPoint`.

A `Fireproof` `BoolValue` child no longer means anything: there's no touch-ignition system in this mode, so it's safe to leave on old map geometry or remove.

## Conventions

- New tunables go in `Constants.luau`, except per-item ones (price, stats, ability params, weapon grip), which go in that item's module under `Items`. Don't hardcode magic numbers in systems.
- New shop item: add `src/ReplicatedStorage/Items/<Kind>/<Name>/init.luau` plus an `init.meta.json` with `ignoreUnknownInstances`, sync, then drop the `Model` (weapons) or `Icon` ImageLabel (abilities, Robux) inside the ModuleScript in Studio. Nothing else needs registering.
- New cross-system signals: prefer `BindableEvent` over polling. Existing examples: `PlayerState.StateChanged`, `CombatSystem.PlayerEliminated`.
- Server creates Workspace instances; they replicate to clients automatically. No remote needed for visual effects (see the pistol tracer).
- Per-frame work goes through `RunService.Heartbeat` (server) or `RenderStepped` (client).
- Phase changes broadcast via the existing `RoundStateRemote` `extra` payload: add fields rather than creating new remotes for round metadata.
- Need a new RemoteEvent? Use the `ensureRemote(parent, name)` pattern at the top of `CombatSystem.luau`: it returns the existing remote if present, else creates one. Don't rely on Studio-authored remotes for new functionality.
- UI text colors: use `colorize(color, text)` helper in `UIController` to wrap text in RichText `<font>` tags. Both labels have `RichText = true` set automatically on first resolve.
- Cosmetic-only client feedback (sounds, screen shake, vignette, damage numbers) belongs in `CombatFeedbackController`: driven by `DamageDealt` / `DamageTaken` / `KillFeed` / `ShotBlocked` remotes. Don't add gameplay logic here; if a feature needs server authority, route it through the existing remotes instead.

## Testing

In Studio, use **Test → Local Server → 2 Players** for end-to-end testing. To shorten iteration, temporarily lower `ROUND_TIME` or `KILL_TARGET` in `Constants.luau`. A plain **Play** session works solo with the default `BOTS_ENABLED`: you plus the bots meet `MIN_PLAYERS`, the match runs under the real rules, and it ends when a combatant reaches `KILL_TARGET` (or on the timer). You start in the lobby and enter with `SPAWN`.

Rojo's file watcher in this OneDrive folder reliably reports created and deleted files but drops plain modifications: after editing a file, check the Studio copy actually changed. Deleting and recreating a file makes the plugin add a second instance next to the stale one instead of replacing it, so don't use that as a workaround; set `.Source` from the command bar or reconnect Rojo instead.

Module state is per-VM: `require` from the command bar or the MCP plugin returns a *fresh* copy of a system, not the one `Main.server` is running, so calling `CombatSystem.shoot` or `BotSystem.remove` from there does not touch live state. Drive tests through the remotes and Workspace instead. The pure-logic checks (`Systems/MatchScoreTest.luau`, `Systems/SpawnPickTest.luau` and the other `*Test` modules) are functions to call, run in a play session's Server VM.

9. A second `SpawnRequest` while `Safe` does nothing. A bot you kill reappears within a few seconds under the same name.
10. As a victim taking damage, a vignette pulse + light camera shake fire; the screen does NOT shake while not being hit. Damage numbers stream above the victim's head.
11. Scoring: the Status line reads `<NAME> LEADS n` once someone has scored (a bot's generated name if a bot leads), the board under the pill lists up to five scorers by kills with their headshots (bots included, yours in orange), Tab opens the scoreboard with every player and bot's kills and deaths this match (the stock Roblox player list never appears) and Tab again closes it, your `KILLS n/20` counts only your own kills, and a kill adds `SHOP_COINS_PER_KILL`.
